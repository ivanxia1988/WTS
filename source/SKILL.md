# 猎聘智能寻访

浏览器由 `scripts/build_workflow.py` 编译出的工作流驱动，Agent 只接触 workflow_ref 和 result_ref；**网络搜索工具**只在步骤 3.5 调研目标公司、以及步骤 15 的市场求证子 Agent 中使用。

## 与用户交互

### 提问

request_user_input 是**独占调用**：它所在的这一轮里没有别的工具调用。固定 skill_name=wts，step_id 见各步。宿主的字段约束：每题最多 8 个选项；label ≤ 80 字，只放选项本身，理由和差异写在 description（≤ 240 字）；prompt ≤ 300 字；用户可自行填写用 allow_custom=true 表达，推荐的填写值放 custom_placeholder。确认需求时，完整需求稿放在问题的 description；如果超过字段限制，先作为普通文本完整输出，description 只放摘要。prompt 始终只写一句简短问题，不重复正文。

**每次让用户选，都给推荐**——推荐统一写在 label 开头：`[推荐] 选项内容`；所有选项的 `recommended` 字段保持 false（宿主的推荐标记每题只允许一个，且会和前缀重复，所以只用前缀）。单选：一项带 [推荐]。多选：前 3 项带 [推荐]（不足 3 个可选项时全标），按推荐顺序排列。自由填写：custom_placeholder 给推荐值。每个推荐在 description 里附一句依据，推荐就是 Agent 自己判断的公开版本，让用户多数时候只需同意。

**用户看到的一律是白话**：选项、画像、播报、报告都写给猎头看。Agent 的规格和记录（需求确认稿、内部报告）写到任务工作目录 `<TASK_WORK_DIR>/wts/` 下的文件里，给用户的文本是从文件渲染出来的视图；title 范围、公司层、置信度、candidate_ref 等内部字段只在文件和决策记录里出现。

新建文件使用 `write_file`；修正已经存在的需求、计划或决策文件使用 `edit_file`。不要用临时脚本绕过字段校验或回改已经执行的历史计划。

### 播报

检索阶段用户只能看到一连串工具调用。用户看见的句子是**猎头句**：另一位猎头听得懂的 1–3 句，只讲用了哪些词、多少人条件对得上、接下来打开几份或换哪家公司。评价说「很匹配」「值得推荐」。姓名、分数、公司、简历内容只在终态报告出现。步骤 11.3 的判断样例按该步写给用户看。播报不占独占调用。

猎头句用中文写。岗位词、技术名词、公司名保持原文，句子主干是中文。

完成标准：每一句去掉任务目录和工具名之后，仍能单独讲给猎头听；句子主干是中文。

只在标了 **播报** 的节点说话。编译失败、改计划、漏写字段：改对并能编译，这一轮不对用户输出任何字。猎聘要重新登录或要验证码时才开口，例：「猎聘要求重新登录，浏览器窗口已打开，请登录后我会自动继续。」

## 执行 SOP

### 1. 取上下文

从任务上下文取得 JD、职位标题（可能缺失）、目标人数、任务 ID、绝对的任务工作目录、绝对的内置 Skill 目录和轮次预算，直接使用运行时提供的绝对路径。

用户在上一次寻访报告后选择了某个备选方向再发起本次任务时，对话历史里会有那个方向的名称和 title 范围：它就是本次的主池，其余全部从零开始——重新拆解、重新澄清、重新确认。唯一延续的是**已看台账**：对话历史里有上一次报告的 `seen_ledger_path` 时，按 `references/seen-and-expand.md` 把它合并进本次的 `<TASK_WORK_DIR>/wts/seen.json`，这些人本次不再打开详情。

### 2. 拆解需求，形成需求确认稿草案

- **标题锚点**：有职位标题时，从标题提取 1–2 个候选人会在简历里逐字写出的短锚点，去掉"工程师""开发""研发""算法""技术专家"等后缀和公司前缀（"千问-AI Agent工程师"→"AI Agent"；"Flink开发工程师"→"Flink"）。没有标题时从 JD 总结一个岗位锚点并标注"[由 JD 总结]"。第一个锚点是**主锚点**，全程固定出现在每条查询里；第二个是**第二锚点**，只作第 1 轮的搭配词。
- **原子化**：JD 是"尚未验证的需求证据"，逐句拆成独立需求。缺失的写"未指定"并保持未指定直到用户回答；推测标 [假设]。缺失、推测和下面三种病症都汇入待澄清清单，按步骤 3 的主题归类。示例——"需要很强的数据能力，北京上海深圳杭州成都均可"：正确拆法是"数据能力是工程/分析/建模哪种？未指定"、"五个城市是工作地还是来源地？未指定"，两条都进待澄清清单。
- **JD 病症**：很多 JD 是从网上抄来再改的，三种常见病识别后打标记，提问在步骤 3 的对应主题：
  - **[CONFLICT] 逻辑矛盾**：两条要求在逻辑上不能同时成立（"3 年以上经验"+"资深架构师职级"；"本科"+"博士优先"；"10 年以上"+"30 岁以下"）。年龄、性别只可作为用户明确指定的站内筛选偏好，不进入硬冲突判定；学校名称、民族、婚育按决策规则直接告知不执行。
  - **[过载] 全能型 JD**：每条单看合理，合起来市场上没有人。信号：反事实测试后必须满足仍 > 5 条；必须满足横跨 ≥ 3 个职能；年限与职级明显不配。
  - **[套话] 模板句**：沟通能力、团队合作、责任心、抗压这类通用句。先试着改写成可观察行为（"跨团队推动项目落地"→ 看项目经历里有无跨部门项目）；改不动的标 [套话]，列入确认稿【备注】供用户捡回。
- **[假设] 的去向**：每个 [假设] 走两条路之一——在澄清轮里问掉，或原样列进确认稿【关键判断】让用户看见。
- **必须满足 / 加分项 / 排除信号**——按用途分类：
  - 必须满足：缺了就做不成岗位，用于搜索和硬筛。判据是**反事实测试**："不满足此条但其余都优秀的人，能否六个月内做成岗位？"答"可能"就降为加分项。重点审查学历、年限、知名公司是否只是能力的代理变量。每条注来源（JD 第 n 条 / 用户确认）。
  - **简历可见性测试**：通过反事实测试的每一条，再问"猎聘详情页的哪个区块能看出来？"（工作经历 / 项目经历 / 技能 / 教育经历 / 自我评价）。答得出来的才留在必须满足或加分项，并记下区块。答不出来的——顶会论文、绩效、口碑、抗压、带团队规模这类简历通常不写的——不删除，进 **面试核实项**（`verify_in_interview`），确认稿和画像里单列一行。这些条不写入必须满足、加分项或排除信号。
  - 加分项：确实正确但只进评分。
  - 排除信号：硬过滤。来源：JD 明确不要、用户补充不要、默认排除。默认排除"近 1 年内多次跳槽"，确认稿中标"默认"，用户可要求去掉。JD 或用户信息明确招聘公司时，记录公司名及依据，加入"当前仍在该公司任职"；曾经任职不排除。仅有推测时在现有澄清环节确认，无法确认则不启用。
  - 模糊素质词按 [套话] 处理。
- **硬性筛选条件**：只收 JD 明确写出、且猎聘页面能验证的地点、学历、工作年限、公司、学校类型、工作内容。未声明的默认"不限"；年限、学历、薪资未填写时同样默认不限，是否该成为必须满足由反事实测试决定，需要裁决时归入同一次澄清的城市与硬边界。JD 里的学历是下限：写「本科」即本科及以上，写「硕士」即硕士及以上。确认稿的 `education` 写下限这一档；用户写明只要这一档、不要更高时，才记下「只要这一档」。站内怎么点见 `references/search-plan.md`。
- **检索关键词**：从 JD 提取最多 8 个非锚点**支持词**，只取可能逐字出现在简历里的原子词——技术、工具、框架、算法、方法、稳定的能力名词（"大模型应用落地"不取，"RAG""LangChain"取；"高并发系统建设"→"高并发"）。同一概念的不同写法归为一个**词族**，一个词族只取一个代表词。前 6 个为**活跃词**，其余为**备用词**。公司名是另一类检索词——**公司词**——由步骤 3.5 单独产生和管理，与支持词互不占额。
- **不做搜索词**：薪资、地点政策、流程偏好、抽象素质、年龄、性别等。它们分别只进硬性筛选、评分项、用户明确确认的站内筛选偏好，或完全不用。
- **站内筛选偏好**：年龄、性别、活跃度、跳槽频率只在用户明确指定猎聘页面条件时记录；分别写入 `site_filters.age_range`、`site_filters.gender`、`site_filters.activity_recency`、`site_filters.job_hop_frequency`，不得由 JD 模糊表达、默认排除信号或模型偏好推断。

完成标准：主锚点、必须满足、硬性筛选条件、站内筛选偏好、检索关键词五项都有明确内容或明确写着"未指定"；面试核实项已单列；待澄清清单已列出全部"未指定"、[假设]、[CONFLICT]、[过载]，并按步骤 3 的主题归好类；[套话] 已单列。

### 3. 判断是否需要澄清

有效 SearchPlan 至少要有一个明确的主锚点，加上至少一个能区分候选人范围的支持词或硬性筛选条件。仅有"产品经理""技术人员""运营"等宽泛岗位名，加"有技术意识""学习能力强"等软性特质，不算有效搜索锚点；软性特质按 [套话] 处理。

**门禁**——五类必答：岗位与职级、核心技能、必须满足的边界、城市、排除信号。每一类都要有结论（JD 写清了算有，用户答了算有）且没有未裁决的 [CONFLICT]，才进需求确认门。目标公司走步骤 3.5，在此不问。另外三种情形无论如何都要问：任务上下文只有职位 ID/名称而没有 JD 正文；只有宽泛岗位名和软性特质；同一描述存在多个会显著改变关键词或硬性筛选条件的合理解释。

**一次澄清**——下表里已触发的主题放进同一次 request_user_input，step_id=clarify-jd。JD 已写清的主题不出现。同一缺口只问一次。宿主一次可以确认多题，不要拆成多轮。

| 主题 | 触发条件 | 题型 |
| --- | --- | --- |
| 岗位定位 | 主锚点不清，或有多种解释 | 单选 + 自定义 |
| 必须满足的裁决 | 有 [过载]，或反事实测试降级了任何一条 | 多选：Agent 给出必须满足名单与降级名单，用户勾选"缺了就不行"的 |
| 矛盾裁决 | 有 [CONFLICT] | 每条三选一：取前者 / 取后者 / 都放宽为加分 |
| 城市与硬边界 | 城市未指定、多城市，或年限/学历是否算硬条件待定 | 城市自由填写；硬边界单选 |
| 站内筛选偏好 | 用户明确提到年龄、性别、活跃度或跳槽频率，但页面预设未确认 | 按页面支持值单选或填写年龄边界；允许不限 |
| 排除信号 | JD 没写"不要什么" | 多选 + 默认项 + 自定义 |

城市专项：实际工作地 ≠ 候选人来源地。JD 出现多个城市要问清几个 HC、最终在哪入职、"均可"是各地有团队还是接受搬迁；JD 列出几十个城市时问"是否有重点城市、真实主阵地在哪"。

站内筛选偏好专项：年龄范围只接受 16–60 的整数边界，至少一个边界；性别只接受男/女；活跃度与跳槽频率只接受 `references/search-plan.md` 列出的页面预设。模糊说法（如“年轻一些”“最近比较活跃”“别太频繁跳槽”）不自行换算，必须请用户选页面预设或选择不限。四类字段都只进 `site_filters`，不写入 `hard_filters`、评分或排序。

收到答案后合并一次。只有答案引出新缺口才再问一次。仍不足以形成有效搜索词时停止并说明缺少什么。

完成标准：五类门禁全部有结论；待澄清清单里没有未处理的 [CONFLICT] 和 [过载]；剩余 [假设] 已标记为待进【关键判断】。

### 3.5 目标公司

城市已确认之后才做这一步，因为调研要按城市找公司。两个分支：

- **JD 已列出目标公司**：照录，每家置信度 1.0，来源标"JD"，跳过调研和提问。
- **JD 未列出**：先用一句白话告知用户（"JD 没有指定目标公司，我先用网络搜索调研一下，再请您确认"），再按 `references/target-company-research.md` 用网络搜索工具调研，产出岗位定位、公司类别和带置信度的公司清单，然后按其提问格式调用 request_user_input，step_id=confirm-target-companies。用户自定义补充的公司置信度 1.0，来源标"用户"；用户勾选调研结果只表示采纳，置信度保持调研值。

**去向**：

- **目标公司**：用户采纳的公司（勾选的调研结果 + 自定义补充）→ 进**目标公司池**，同时进加分项和市场洞察。置信度只用于排序和记录。
- **公司类别**：调研得到的类别本身，写方向不列名 → 进市场洞察。

**目标公司池**是贯穿全程的公司词候选清单，记在决策记录里，每家一行：公司名｜来源｜置信度或命中人数｜未用 / 已用 / 人不够。两个来源：

- **初始**：本步骤的目标公司。用户自定义补充的排最前（按填写顺序），其后是勾选的调研公司，按推荐顺序。全部直接标**未用**。
- **扩充**：第 1 轮起，每轮评分后把评分子 Agent 返回的 `company_hits` 并入池子，来源标"高分候选人"，记命中人数；已在池中的公司累加命中人数。这是第 1 轮之后新公司的唯一来源；扩充公司只作公司词和市场洞察，加分项只认初始目标公司。

**公司词**的全部使用规则集中在此：

- 已确认的招聘公司不进入目标公司池，也不从候选人履历中重新加入；按已确认的全称或简称识别，不自行扩大到集团或关联公司。
- 每轮主路径最多带一个公司词，一家公司只用一次；第二路永远只有锚点和支持词。选择顺序：未用的自定义公司按填写顺序 → 未用的调研公司按推荐顺序 → 未用的扩充公司按命中人数。反思提建议，Controller 拍板。没有未用的候选时主路径只用锚点和支持词。
- 用过且硬筛够额 → **已用**；本轮触发补搜 → **人不够**。已用和人不够都不再选。
- 公司词是检索词而非硬条件——公司进 hard_filters 的唯一途径仍是 JD 或用户明确要求"只要这些公司"。

用户全部不选或选"不限"时目标公司写"不限"，池子初始为空，主路径可以不带公司词；第 2 轮起仍按高分候选人扩充；调研得到的岗位定位和公司类别保留给市场洞察。

完成标准：目标公司有明确结论（清单或"不限"）；每家公司有置信度和来源；目标公司池已按推荐顺序建好。

### 4. 需求确认门

写确认稿之前先完成两件事：

- **城市分层**：城市 A=实际工作地/主池，B=可搬迁来源，C=仅观察不入池。
- **主池与备选方向**：**主池**是 Agent 判断最可能的方向 = 精确 title × 目标公司 × 城市 A 层，是本次 1–3 轮检索唯一服务的对象。**备选方向**是 Agent 判断"不是最可能、但也有可能"的其他解释——相邻 title、相邻行业、可迁移背景、B 层城市的组合——最多 2 个，每个一行写清名称、title 范围、与主池的差别。备选方向只记在决策记录里，在步骤 16 呈现；确认稿只写主池。主池拿不准时把它当作待澄清项在步骤 3 问。

然后按 `references/requirements-draft.md`：把需求确认稿写成 `<TASK_WORK_DIR>/wts/requirements/vN.json`，从它渲染**候选人画像**，做完决策无损核对后先以普通文本输出画像，再调用 request_user_input，step_id=confirm-requirements，prompt 一句"这是我理解的候选人画像，可以开始找了吗？"，选项两个："[推荐] 确认，开始找人" / "我要改某一处"（allow_custom，填写改哪里）。用户看到的只有画像；确认稿是 Agent 的规格，只存在于文件里。

用户选"我要改某一处"或在自定义里质疑某处时，只改确认稿被质疑的部分，写新版本文件，重新渲染完整画像再次请求确认。"没有补充""OK 吧"这类含糊回复视为未确认，同样重新呈现再问一次。

检索开始后用户补充需求时：写新版本文件，只在当前轮结束、下一轮 SearchPlan 编写前生效；纯约束型补充（如新增地点限制）只更新硬性筛选条件和评分项；版本切换后再派评分子 Agent 重评，重建榜单。步骤 11.3 的尺度调整当轮生效，见该步。

完成标准：用户选了"确认，开始找人"，该版本文件冻结为当前需求版本；画像里每条必须满足、硬性条件、排除信号、关键判断都能在文件里找到对应。

**播报**："需求已确认，接下来检查浏览器和猎聘登录。"

### 5. 检查浏览器

调用 browser_embedded_status(inspect_page=false) 检查通用内置浏览器、通用插件和本地传输是否可用。猎聘登录状态由下一步判断。

完成标准：内置浏览器、插件、本地传输的状态已读到。

### 6. 登录前置

编译并执行登录前置工作流：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" preflight --task-id TASK_ID --iteration 0 --task-work-dir "/ABSOLUTE/TASK_WORK_DIR"
```

把返回的 workflow_ref 传给 browser_run_workflow(task_id, workflow_ref)。登录、验证码和风控识别已编译进工作流；命中后浏览器显示窗口等待用户处理，按异常格式播报需要用户做什么，等用户处理完再继续。

完成标准：前置工作流已返回；需要登录时已按异常播报并等用户处理完。

**播报**（前置就绪后）："猎聘已登录，开始第 1 轮检索。"

### 7. 编写第 N 轮 SearchPlan

读当前需求版本文件（`<TASK_WORK_DIR>/wts/requirements/` 下 N 最大的 vN.json）和 `references/search-plan.md` 的字段、路径、限额契约，把需求版本拆为两路查询、站内筛选、硬性条件和语义评分项，写入契约规定的 iteration-N.json。

- **主路径查询（利用）**：第 1 轮的起手形态 = 主锚点 + 2 个不同词族的支持词 + 1 个公司词（按步骤 3.5 的规则选，没有则省去）。支持词里第二锚点算一个，其余优先核心技能、框架工具而非泛领域词；选哪两个由 Agent 判断。第 2 轮起形态由 Agent 按上一轮结果调：召回少就减到 1 个支持词或换公司词，召回多而噪音大就保留 2 个；支持词从活跃词中取不同词族，优先沿用带来新可推荐候选人的组合。
- **第二路查询（探索）**：第 2 轮起才有。有待试词时 = 主锚点 + 该待试词（**PRF 探针**）；否则 = 主锚点 + 1 个未试词族的支持词，优先级最高的备用词优先（**通用探索**）；两者都没有则本轮只有主路径。
- 一条查询内词族不重复；第二路与主路径本轮的非锚点词族不同；已发出过的词组合不再重复。关键词只来自当前需求版本的锚点、支持词、待试词或公司词。三轮全部服务于主池，title 范围、公司层、城市层中途保持不变。
- **site_filters**：取自硬性筛选条件中页面有控件的字段，以及用户明确确认的站内筛选偏好；学历按 `references/search-plan.md` 的下限规则写。公司每轮最多一个，多公司 OR 名单只保留在 `hard_filters.company`。年龄、性别、活跃度、跳槽频率只写站内字段，不写硬筛。岗位意图由关键词表达。
- **hard_filters**：全部明确的硬性筛选条件，以及排除信号中页面数据能验证的项。
- **semantic_criteria**：必须满足、加分项、排除信号，照录当前需求版本。
- **requirement_version**：从第 1 轮起写入当前已确认需求版本。同一版本只允许调整查询和合理的站内筛选，不得替换或删除 hard_filters、semantic_criteria。
- **decision_basis**：第 2 轮起保存截至上一轮的全部候选人原始评分、证据引用、首次评分轮次、PRF 判定和下一步；退出 Top 10 的候选人也保留。Builder 使用真实执行工作流中的计划快照校验，不能通过回改旧 iteration 文件绕过一致性检查。

完成标准：iteration-N.json 已写入，两路查询、筛选和评分项都能回溯到当前需求版本。

### 8. 编译本轮搜索工作流

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" search --task-id TASK_ID --iteration N --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --plan-file "/ABSOLUTE/TASK_WORK_DIR/wts/search-plans/iteration-N.json"
```

默认使用拟人交互；需要即时操作时可显式加 `--interaction-mode direct`。`human` 模式由宿主执行渐进移动、逐字输入和有界滚动，不保证规避站点风控；执行 workflow_ref 时不能临时覆盖 Builder 固化的模式。

校验失败时按返回的错误原因原地修正同一个 iteration-N.json 并重新编译一次，这一轮不对用户输出任何字；仍失败则停止。

完成标准：编译已成功；校验失败时同一个 `iteration-N.json` 已原地改过并重新编译一次，或已停止。

### 9. 执行工作流

**播报**（执行前，必须预告）：本轮用哪几组词、大概几分钟、期间不会有新消息。例："第 2 轮开始，这轮用「AI Agent + LangGraph」和「AI Agent + RAG」两组词检索，预计 3–5 分钟，期间不会有新消息。"

执行 browser_run_workflow 读取两路卡片。对照台账挑出未看的人，按 `references/seen-and-expand.md` 采集所选详情。每轮主路径最多采满上限（默认 5 人）、第二路最多 3 人，两路不重复。

**补搜**——search 返回后先数主路径**可采**人数：卡片硬筛为 matched/unknown、且不在已看台账里的人数。查询带了公司词、该公司不是硬条件、可采人数小于主路径上限 → 本轮必须补搜一次：

1. 先采集这批人（0 人则跳过第一次采集），公司池标「人不够」。
2. 按 `references/search-plan.md` 的补搜计划写文件、编译、再搜一次（只走主路径，去掉该公司词）。
3. 从补搜卡片采集差额（上限减去本轮主路径已采集数）。
4. 每轮最多一次。无公司词、或公司是硬条件时不补搜，有谁采谁。

第二路照常采集；补搜只重跑主路径。两批详情收齐后再进入步骤 10–11，本轮只评一次。补搜不计入轮次，也不代替扩张。

**播报**（补搜前）："这家公司符合条件的人只有 N 位，我先打开这几份，再去掉公司限制补找。"

完成标准：本轮搜索与第一次采集已执行（可采为 0 且将补搜时可省第一次采集）；若触发补搜，补搜与第二次采集已执行。

### 10. 读取结果

检查 status、error_code、summary.metrics、summary.sections 和业务 summary。对每次采集的 success 或 partial 结果，运行 `scripts/score_inputs.py --task-id TASK_ID --result-ref RESULT_REF --task-work-dir "/ABSOLUTE/TASK_WORK_DIR"`（脚本路径以当前 Skill 目录为根）。脚本写出单人详情、只返回索引。主 Agent 用索引追加台账（见 `references/seen-and-expand.md`），把待评人的 `profile_path` 交给步骤 11。partial 时读 search 的 unsupported_filters。站内筛选降级只是召回范围没缩小；有 `hard_filter_fallback` 的条件继续由卡片和详情硬筛执行。年龄、性别、活跃度、跳槽频率没有本地硬筛回退，页面操作失败时必须报告未验证，不能承诺候选人已满足。失败原因读 failures 的错误字段。

完成标准：本轮全部详情与失败记录已进入索引和台账；若有补搜，两批都已入账；partial 时已查明筛选降级原因。

**播报**：用了哪些词、各看到多少人、打开了几份简历、多少人条件对得上、几位之前看过所以跳过；补搜过就把两次的人数说在一段里。页面上某个条件没筛上时，同一段里说清是哪一个，后面会用简历再看。

### 11. 隔离评分

仅对索引里详情硬筛 matched/unknown、且本需求版本尚未评分的人评分，跨轮按 candidate_ref 去重。派一个评分子 Agent：把 `references/scoring.md` 路径、当前需求路径、本轮待评人 `profile_path`、本轮 N 传给它，任务说明只写「按该文件一次返回规定 JSON」。消费 `{candidate_scores, labels, company_hits}`：分数写入 decision_basis，`labels` 用于扩张门和播报，`company_hits` 按步骤 3.5 并入公司池。沿用旧分时逐字复制已有 `candidate_scores`；需求变更或明确算错才重评并写 correction_reason。

完成标准：本轮每位 matched/unknown 候选人都有评分记录；Top 10 与目标公司池已更新。

**播报**：本轮评了几人、新增加几位值得推荐、几位很匹配、名单上现在几人；从这些人里新记下几家公司（只说数量）。第 1 轮这则播报之后进入步骤 11.3；第 2 轮起进入步骤 11.5。

### 11.3 尺度确认（仅第 1 轮）

本轮有评分记录时，先给用户看判断样例，再决定是否扩张。没有评分记录就进入步骤 12。第 2 轮起不执行本步。

样例从本轮 `labels` 里取 2 位值得推荐的（优先很匹配）和 1 位不推荐的；某一类不足就有几位写几位。每人两行，只根据该人卡片和 `evidence_summary` 来写：第一行是什么样的人，第二行是这样判的理由。姓名、分数和公司全称留在记录里，公司写成行业或类型。

先把这几则样例用普通文本输出，再调用 request_user_input，step_id=calibrate，prompt 一句「这个尺度对吗？」。单选，推荐「尺度对，继续找」：

- 「[推荐] 尺度对，继续找」
- 「偏松，这样的人不该推荐」（allow_custom，填写哪一条必须满足或加分项要更严）
- 「偏严，这样的人可以推荐」（allow_custom，填写哪一条可以放宽）

选了尺度对，用本轮 `labels` 进入步骤 11.5。选了偏松或偏严且写明了改哪一条：只改那一条，按 `references/requirements-draft.md` 写新版本，不重新确认画像；再派评分子 Agent，传入 `references/scoring.md` 路径、新需求路径、已评过的人的 `profile_path`、本轮 N，任务说明只写「按该文件一次返回规定 JSON」，`correction_reason` 写「尺度调整」。用返回的 `labels` 进入步骤 11.5，`company_hits` 按步骤 3.5 并入公司池。没写清改哪一条时，用同一步再问一句。

完成标准：已拿到用户选择；若改了标准，新版本文件已写入，已评的人已按新版本重评，扩张门用的是重评后的 `labels`。

**播报**：尺度照旧，或改了哪一条、已按新标准重新看过；接下来是继续从这一页看人，还是这一页先到此为止。

### 11.5 轮内扩张（可选，可重复）

第 1 轮在步骤 11.3 之后、第 2 轮起在评分之后，按 `references/seen-and-expand.md` 判断扩张门并执行。不达标进步骤 12。

完成标准：每次扩张都有计划文件、运行结果、台账追加和评分记录；挑人依据在决策记录里。

### 12. PRF（伪相关反馈）：先试后晋升

派一个 PRF 子 Agent：把 `references/prf.md` 路径、当前需求路径、本轮 `labels`、索引里的 `profile_path`、本轮搜索摘要（各路 query、新增/重复/可推荐人数）、已有 `prf_decision`、已完成轮数传给它，任务说明只写「按该文件一次返回规定 JSON」。消费返回的 `prf_decision`，写入本轮决策记录。

完成标准：本轮 `prf_decision.status` 已按对账表落下。

### 13. 反思（只有建议权）

派一个反思子 Agent：把 `references/reflect.md` 路径、本轮搜索摘要、`labels`、目标公司池、当前词表、步骤 12 的 `prf_decision`、当前站内筛选传给它，任务说明只写「按该文件一次返回规定 JSON」。消费返回的反思建议，交给步骤 14。Controller 仍由主 Agent 做；Builder 没有 `reflect` 子命令。

完成标准：反思 JSON 里对活跃词、站内筛选、下一公司各有表态。

### 14. Controller 决策

**强池** = Top 10 已满且强匹配 ≥ 5。

**最大轮次** = min(轮次预算, 3)。**已完成轮数**是本轮在内、已经执行完步骤 7–14 的轮数；轮内扩张和补搜不改变轮数。开始第 N+1 轮的唯一条件是"已完成轮数 < 最大轮次"且下面的判定为继续：已完成 2 轮时 2 < 3，第 3 轮照常开始并完整执行。

Controller 是停止与下一轮关键词的最终决策者，按下列优先级判定：

1. 致命错误，或有外部副作用的动作效果未对账 → 终止或暂停，不报告终态。
2. 已完成轮数 ≥ 最大轮次 → 硬停。
3. 没有任何可执行查询（活跃词、备用词、待试词、仅锚点查询都已用尽）→ 以"词族耗尽"异常终止。
4. 质量门：强匹配 ≥ 3 或已成强池 → 可停；但有新候选人的轮次不足 2 且仍有未试词族 → 继续。强匹配 < 3 时：有未试词族 → 继续；没有 → 先放宽一次（激活备用词或换相邻写法）再允许低质量停止。
5. 救援（决定继续但没有可选活跃词族时，按序执行一步）：激活备用词 → 试跑已存在的待试词 → 仅主锚点查询（最多一次）→ 以"词族耗尽"停止。

继续时：输出下一轮主路径关键词（含下一个公司词，如有）与非地点筛选调整，对上轮反思逐条表态（接受 / 部分接受 / 拒绝），回到步骤 7。停止时：记录确定性停止原因——强匹配足够、新增候选不足、多轮无进展、达到最大轮次、词族耗尽、预算——进入步骤 15。

完成标准：决策记录里要么有确定性停止原因，要么有下一轮关键词，并且对上轮反思逐条写了接受、部分接受或拒绝。

**播报**（每轮小结）：这轮各组词带来多少新人、多少是之前看过的；累计多少位值得推荐、多少位很匹配；继续就说下一轮换哪组词和原因，停止就说原因并告诉用户马上给报告。

### 15. 终态报告

把最终 `decision_basis` 写到 `<TASK_WORK_DIR>/wts/final-decision.json`，其中 completed_iteration 是最后已完成轮次、next_action.action 为 report。执行 `settle --iteration N`，N 仍是最后已完成轮次，不新增第 N+1 轮。Builder 生成 `<TASK_WORK_DIR>/wts/final-report-data.json`。

写市场观察之前，派一个市场求证子 Agent：把 `references/market-research.md` 路径、当前需求路径、`final-report-data.json` 路径、步骤 3.5 的公司调研结论传给它，任务说明只写「按该文件一次返回规定 JSON」。猎聘上的人数和分数只用 settle 结果；公开资料用它返回的结论和来源。再按 `references/final-report.md` 渲染用户视图，不扫描结果目录或重新评分。

report.json 里要带 `seen_ledger_path`（本次台账的绝对路径）和 `not_recommended`（看过但没推荐的人数与原因汇总）；用户视图对没推荐的人只说数量和原因，不列个人。

完成标准：report.json 已写入；用户视图里每位 Top 10 候选人都有一行和真实链接。

### 16. 方向选择

终态报告输出后，调用 request_user_input，step_id=next-direction，用白话问一句"这个方向找完了，要不要换个方向继续找？"，单选，允许自定义：

- 每个备选方向一个选项，写成招聘用户听得懂的一句话（"从做过 XX 的人里继续找"）。
- 固定加一个"先到这里"选项。没有备选方向时只留这一项。
- 推荐一项并附依据：可推荐人数未达目标且有备选方向时推荐最接近主池的那个；已达目标或没有备选方向时推荐"先到这里"。

这是本 Skill 的最后一个动作。用户的选择在本 Skill 之外处理：选了某个方向，那是一次新的寻访任务，从步骤 1 重新开始，主池即该方向；选了先到这里，结束。

完成标准：request_user_input 已发出，选项是全部备选方向加上"先到这里"，其中一项标了推荐。

## 决策规则

- 主 Agent 只消费卡片、索引、各子 Agent 返回值和 Builder 回执。可推荐、强匹配以 `labels` 和之后的 Builder 回执为准。`scoring.md` / `prf.md` / `reflect.md` / `market-research.md` 与详情文件只把路径交给对应子 Agent。
- 年龄、性别仅可作为用户明确确认的站内筛选（`site_filters.age_range`、`site_filters.gender`），不得写入 `hard_filters`，也不参与评分、排序、硬冲突判定或市场洞察；页面操作失败时按 `unsupported_filters` 报告未验证。学校名称、民族、婚育仍不写入检索、站内筛选、评分、排序、硬冲突判定或市场洞察，用户提出时说明不予执行。
- 零结果是有效的查询结果，进入正常的评分、反思和 Controller 决策；工具错误、超时或页面失败是失败，不记作零结果。
- 未被容错块捕获的 TARGET_NOT_FOUND、WAIT_TIMEOUT、PAGE_STATE_NOT_RECOGNIZED，或工作流引用失效，都结束当前轮；只有调整搜索计划、更新 Skill 页面规则或恢复明确的人工作业状态后，才重新编译执行。
- 有外部副作用的动作出现网络错误、超时或效果未知时，先读取运行结果**对账**：已有明确观察则消费结果；证明未产生效果后才允许在下一轮重新编译执行；仍无法确定时暂停并说明。
- 只有前置或搜索工作流明确返回 login_required 时才判断为未登录；其他页面错误按各自的错误码处理。
