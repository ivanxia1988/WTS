# 猎聘智能寻访

本 Skill 是猎聘渠道知识的唯一所有者。Agent 负责理解 JD 和作出轮次决策；Skill Builder 负责把搜索计划、渠道资产和流程模板编译为 browser.workflow.v1；通用浏览器只解释工作流，不得依赖任何 liepin.* capability。

寻访分两个阶段，一条硬门禁：先把 JD 拆成需求确认稿并取得用户明确确认，确认之前不调用任何浏览器工具；确认后按轮次执行两路检索（主路径 + 第二路），每轮一份 SearchPlan、一次工作流执行、一轮逐候选评分、一次反思、一次 Controller 决策。

每轮评分和决策必须形成可复用的结果，不能只留在内部思考中。第 2 轮起，随现有 SearchPlan 的同一次写入保存 `decision_basis`，包含当前需求版本、截至上一轮的全部评分及证据引用、PRF 判定、已定关键词和下一步；结构见 [搜索计划契约](references/search-plan.md#评分与决策复用)。继续搜索沿用已有写入/编译调用；终态另存最终评分快照并做一次本地结算，不新建评分服务。

## 进度播报

确认之后的检索阶段可能持续很久，用户只能看到一连串工具调用。播报是给等待中的用户看的进度说明：在下面列出的节点，先用普通文本输出一段播报，再发起下一次工具调用。播报不是新的工具调用，也不改变 request_user_input 必须是唯一工具调用的规则；确认门本身就是和用户的对话，不再另外播报。

每段 1–3 句，固定说三件事：刚完成了什么、已确认的结果数字、接下来做什么。只写数量，不写候选人姓名、分数、公司或简历内容，姓名和分数只在终态报告出现。评分人数和推荐人数只能取实际完成的评分；继续下一轮时，评分播报与轮次小结合并到 Builder 返回 `decision_receipt` 之后，直接使用其中的计数，不在写计划前预报。用招聘用户听得懂的白话，不出现 workflow_ref、result_ref、candidate_ref、iteration-N.json、SearchPlan、PRF、Controller、hard_filters、site_filters 等内部名词，也不贴原始错误文本；检索用的关键词本身可以说。

播报节点（每轮约 5 段）：

1. 需求确认稿冻结后（步骤 4）："需求已确认，接下来检查浏览器和猎聘登录。"
2. 浏览器与登录就绪后（步骤 6）："猎聘已登录，开始第 1 轮检索。"
3. 本轮开始检索前（步骤 9 之前）：必须预告本轮用哪几组关键词、预计几分钟、期间不会有新消息。例："第 2 轮开始，这轮用「AI Agent + LangGraph」和「AI Agent + RAG」两组词检索，预计 3–5 分钟，期间不会有新消息。"
4. 检索结束、结果读完后（步骤 10）：两组词各看到多少人、多少人进入详情、多少人通过硬性条件。
5. 评分完成后（步骤 11）：本轮评了几人、新增几位可推荐、几位强匹配、榜单目前几人。
6. 轮次决策后（步骤 14，即每轮小结）：继续则说下一轮换什么方向；停止则说一句原因，并告知马上给出报告。

异常状态用同一格式：需要用户登录或处理验证码、触发风控、致命错误、效果不确定而暂停时，说清发生了什么、需要用户做什么或系统接下来会怎样。例："猎聘要求重新登录，浏览器窗口已打开，请登录后我会自动继续。"

## 执行 SOP

### 1. 取上下文

从任务上下文取得 JD、职位标题（可能缺失）、目标人数、任务 ID、绝对的任务工作目录、绝对的内置 Skill 目录和轮次预算。任务 ID 只使用字母、数字、点、下划线和短横线。直接使用运行时提供的绝对路径，不要自行探测或另建工作目录。

### 2. 拆解需求，形成需求确认稿草案

- **标题锚点**：有职位标题时，从标题提取 1–2 个候选人会在简历里逐字写出的短锚点，去掉"工程师""开发""研发""算法""技术专家"等后缀和公司前缀（"千问-AI Agent工程师"→"AI Agent"；"Flink开发工程师"→"Flink"）。没有标题时从 JD 总结一个岗位锚点并标注"[由 JD 总结]"。第一个锚点是**主锚点**，全程固定出现在每条查询里；第二个是**第二锚点**，只作第 1 轮的搭配词。
- **原子化**：JD 是"尚未验证的需求证据"，逐句拆成独立需求。缺失的写"未指定"，禁止按常识或市场经验补全；推测标 [假设]，矛盾标 [CONFLICT]，不得静默修复。缺失和矛盾汇入待澄清清单。示例——"需要很强的数据能力，北京上海深圳杭州成都均可"：不得把"数据 +（北京 OR 上海 OR ...）"直接当条件；正确拆法是"数据能力是工程/分析/建模哪种？未指定"、"五个城市是工作地还是来源地？未指定"，两条都进待澄清清单。
- **必须满足 / 加分项 / 排除信号**——按用途分类，不按"重要程度"：
  - 必须满足：缺了就做不成岗位，用于搜索和硬筛。判据是反事实测试："不满足此条但其余都优秀的人，能否六个月内做成岗位？"答"可能"就降为加分项。重点审查学历、年限、知名公司是否只是能力的代理变量。每条注来源（JD 第 n 条 / 用户确认）。
  - 加分项：确实正确但不用于搜索，只进评分。
  - 排除信号：硬过滤。来源：JD 明确不要、用户补充不要、默认排除。默认排除初始只有"近 1 年内多次跳槽"，确认稿中标"默认"，用户可要求去掉。
  - 模糊素质词（抗压、fast-paced、懂业务）改写成可观察行为，改不了就进待澄清清单，不直接进任何一级。
- **硬性筛选条件**：只收 JD 明确写出、且猎聘页面能验证的地点、学历、工作年限、公司、学校类型、工作内容。未声明的默认"不限"。
- **检索关键词**：从 JD 提取最多 8 个非锚点**支持词**，只取可能逐字出现在简历里的原子词——技术、工具、框架、算法、方法、稳定的能力名词（"大模型应用落地"不取，"RAG""LangChain"取；"高并发系统建设"→"高并发"）。同一概念的不同写法归为一个**词族**，一个词族只取一个代表词。前 6 个为**活跃词**，其余为**备用词**。
- **不做搜索词**：薪资、地点政策、流程偏好、目标公司清单、抽象素质、受保护属性。它们分别只进硬性筛选、评分项，或完全不用（见决策规则中的敏感信息条）。

完成标准：主锚点、必须满足、硬性筛选条件、检索关键词四项都有明确内容或明确写着"未指定"；待澄清清单已列出全部"未指定"与 [CONFLICT]。

### 3. 判断是否需要澄清

有效 SearchPlan 至少要有一个明确的主锚点，加上至少一个能区分候选人范围的支持词或硬性筛选条件。仅有"产品经理""技术人员""运营"等宽泛岗位名，再加"有技术意识""学习能力强"等软性特质，不算有效搜索锚点；软性特质只进评分项。

六类必答：岗位与职级、核心技能、必须满足的边界、城市、公司方向（名单 / 类型描述 / 不限）、排除信号。任一类未经用户确认或存在 [CONFLICT]，不得进入需求确认门。其他必须澄清的情形：任务上下文只有职位 ID/名称而没有 JD 正文；只有宽泛岗位名和软性特质；同一描述存在多个会显著改变关键词或硬性筛选条件的合理解释。

城市：实际工作地 ≠ 候选人来源地。JD 出现多个城市必须问清几个 HC、最终在哪入职、"均可"是各地有团队还是接受搬迁；JD 列出几十个城市时，必须问"是否有重点城市、真实主阵地在哪"。年限、学历、薪资未填写时默认不限、不追问，也不自行补成硬条件——它们是否该成为必须满足，由反事实测试决定。

需要澄清时，调用 request_user_input，设置 skill_name=wts、step_id=clarify-jd，根据当前缺口集中提出 1–3 个问题，只问会改变确认稿内容的问题。能从上下文归纳出少量互斥方向时使用单选并给出推荐理由、允许自定义；否则使用自由文本询问目标岗位/方向、核心职责和必须技能。该调用必须是当前轮唯一的工具调用，不得同时检查浏览器、写计划或执行命令。收到答案后合并进需求确认稿草案并从步骤 2 继续，不重复已完成工作；同一信息缺口只澄清一次，回答后仍不足以形成有效搜索词时停止并说明缺少什么，不要猜测执行。

### 4. 需求确认门

呈现确认稿之前先完成三件事：

- **目标公司**：只来自 JD 明确写出或用户提供（公司名单，或"什么类型的公司"的描述），本 Skill 不做公开研究、不自行补公司名；用户没给就写"不限"。有信息时按用途分层：A 层=直接来源，B 层=可迁移来源（要求候选人展示可迁移证据），C 层=只写方向不列名；不按知名度分层。用户给出的公司互相冲突时不求并集：反推各自代表的属性（规模、客户类型、0到1 能力等），让用户排序哪个才是必须。
- **城市分层与可迁移背景**：城市 A=实际工作地/主池，B=可搬迁来源，C=仅观察不入池。可迁移背景 ≤3 条，写清哪些相邻 title/行业的人也能干、各自注意什么。
- **池子派生**：每个池子 = title 范围 × 公司层 × 城市层 × 可迁移背景。主池必有（精确 title × 公司 A 层 × 城市 A 层）；迁移/转型池按可迁移背景和 B 层组合，附加要求写明（如"须有可迁移证据"）；≤3 个，按优先级排序；分池拿不准就问。当前版本的检索（步骤 5-15）不按池执行，【池子】仅供用户确认并留给后续接入。

然后调用 request_user_input，设置 skill_name=wts、step_id=confirm-requirements。把下面模板的完整确认稿放入 `questions[0].description`（支持 Markdown，最多 3000 字），`questions[0].prompt` 只写“是否确认这份需求，按此开始寻访？”等简短问题（最多 300 字）；提供确认/需要调整的选择及自定义输入。不要把整份确认稿塞进 prompt，也不要为满足长度截掉待确认条件。该调用同样必须是当前轮唯一的工具调用。若返回参数修正提示，按提示修正并重新调用本工具，不要只输出普通文字问题后结束。

```text
# 需求确认稿 vN

【岗位】标题 · 主锚点 / 第二锚点（来源：标题 / JD 总结）· 职级/年限
【岗位使命】入职后要做成什么（一行）
【必须满足】≤8 条，每条一行，行尾注来源
【加分项】按重要性排序，一行列举
【排除信号】逐条列出；默认排除标"默认"
【硬性筛选条件】地点 / 学历 / 工作年限 / 公司 / 学校类型 / 工作内容，未指定写"不限"
【站内筛选偏好】活跃度 / 跳槽频率，只列用户明确指定的页面预设，未指定写"不限"
【检索关键词】活跃词 ≤6 · 备用词 ≤2，各注词族
【不做搜索词】薪资、地点政策、公司清单、抽象素质等，注明去向（评分 / 筛选 / 不用）
【城市】A=主池；B=可搬迁来源；C=仅观察不入池
【目标公司】来源：JD / 用户提供 / 不限；有信息时 A 层、B 层各列公司名+一句话理由，C 层只写方向
【可迁移背景】≤3 条：哪些相邻 title/行业的人也能干，各自注意什么
【池子】≤3 个，每池一行：名称｜title 范围｜公司层｜城市层｜附加要求｜优先级（仅供确认，当前检索不按池执行）
【备注】未指定但不阻塞的点（可空）
```

用户明确回复确认后，该版本冻结为当前需求版本，输出播报节点 1，进入步骤 5。用户质疑某处时只改被质疑部分，版本号 +1，重新呈现完整确认稿再次请求确认；只回复"没有补充"不算确认，要问一次是否确认。

检索开始后用户补充需求时：生成新版本，只在当前轮结束、下一轮 SearchPlan 编写前生效；纯约束型补充（如新增地点限制）只更新硬性筛选条件和评分项，不为它编造检索词；版本切换后，所有已评分候选人按新版本重评，Top 10 重建。

### 5. 检查浏览器

调用 browser_embedded_status(inspect_page=false) 检查通用内置浏览器、通用插件和本地传输是否可用。该工具不负责判断猎聘登录状态。

交互模式沿用用户在当前任务中选择的模式。未指定时使用渠道资产 `assets/channel/liepin.json` 的 `interaction_mode`（当前默认 `human`，启用拟人操作）。用户要求拟人操作时，后续 preflight 和每轮 search 的 Builder 命令都追加 `--interaction-mode human`；要求恢复原有即时操作时追加 `--interaction-mode direct`。无需额外询问模式，也不要把它写进 SearchPlan 的业务筛选字段。

`human` 由浏览器统一执行渐进鼠标移动、短暂停顿、逐字输入与分段滚动，详情抽取前有限滚动并等待页面稳定。Builder 回执返回实际模式，执行时仅传 `workflow_ref`，不覆盖已编译模式；不支持该能力时停止说明，不静默退回 direct。拟人模式不保证避免风控，验证码与风控提示仍按既有流程交给用户处理，不能通过切换模式自动重试失败工作流。

### 6. 登录前置

编译并执行登录前置工作流：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" preflight --task-id TASK_ID --iteration 0 --task-work-dir "/ABSOLUTE/TASK_WORK_DIR"
```

只把 Builder 返回的 workflow_ref 传给 browser_run_workflow(task_id, workflow_ref)。登录、验证码和风控识别由 Skill 编译进 page.detect；通用浏览器命中后显示窗口等待用户处理，不要尝试绕过，并按异常格式播报需要用户做什么。前置返回就绪后输出播报节点 2。

### 7. 编写第 N 轮 SearchPlan

首次编写计划时读取搜索计划契约；后续沿用已读契约，不因进入下一工具重复读取。把当前需求版本拆为关键词、站内筛选、硬性条件和语义评分项。计划字段用 primary_query 写主路径，第 2 轮起才写 secondary_query；第 1 轮不得写第二路。第一轮搜索必须直接创建 iteration-1.json，后续轮次依次使用 iteration-2.json、iteration-3.json……第 N 轮计划写到唯一合法路径：

```
<TASK_WORK_DIR>/wts/search-plans/iteration-N.json
```

iteration-0 只保留给 preflight，绝不能用于搜索计划。首次创建文件用 write_file；同轮纠错用 edit_file 修改同一个 iteration-N.json，write_file 不能覆盖已存在文件。不得创建草稿、副本或把长 JSON 内联进命令，也不得回改已执行的历史计划来通过校验。

轮次范围：最少 1 轮、最多 5 轮；最大轮次取轮次预算与 5 的较小值。

每轮 SearchPlan 的内容：

- **主路径查询（利用）**：第 1 轮 = 主锚点 + 第二锚点；没有第二锚点则 = 主锚点 + 1 个最强支持词（优先核心技能、框架工具，而非泛领域词）。第 2 轮起 = 主锚点 + 1–2 个不同词族的活跃支持词，优先复用上一轮带来新可推荐候选人的词族，形成尚未发出过的新组合；不照搬已执行的整条查询。
- **第二路查询（探索）**：第 1 轮不设。第 2 轮起，有待试词时 = 主锚点 + 该待试词（**PRF 探针**）；否则 = 主锚点 + 1 个未试词族的支持词，优先级最高的备用词优先（**通用探索**）；两者都没有则本轮只有主路径。
- 一条查询内词族不重复；第二路不复用主路径本轮的非锚点词族；已发出过的词组合不再重复。关键词只来自当前需求版本的锚点、支持词或待试词，用自然语言词，不写布尔语法。
- **site_filters**：只用地点、学历、工作年限、公司、学校类型，取自硬性筛选条件。公司名称使用 `company: ["字节"]`，当前每轮最多一个公司关键词；多公司 OR 名单保留在 `hard_filters.company`，不要擅自取第一家公司缩小召回。工作内容只进硬筛。岗位意图由关键词表达，不用职位筛选。公司筛选的控件定位、联想选择、确定和生效验证由 Builder 执行，见[搜索计划契约](references/search-plan.md#公司名称筛选)。
- **站内筛选偏好**：还支持 `site_filters.activity_recency`（活跃度）和 `site_filters.job_hop_frequency`（跳槽频率），取用户明确确认的页面预设；未指定或不限时省略。这两项不写入 hard_filters，不从简历文本猜测；默认的“近 1 年内多次跳槽”也不能自动换算为“近 3 年不超过 2 段”等预设。值映射和点选生效规则见[下拉筛选](references/search-plan.md#活跃度与跳槽频率)。
- **requirement_version**：从第 1 轮起填写已确认需求版本，与 decision_basis 中的版本一致。
- **hard_filters**：全部明确的硬性筛选条件，以及排除信号中页面数据能验证的项。同版本跨轮保持不变；换查询词只改 primary_query/secondary_query，不要把每轮查询词同步写进 required_keyword_groups。只有用户明确确认必需的关键词才属于硬条件。
- **语义评分项**：必须满足、加分项、排除信号，照录当前需求版本。
- **详情预算**：主路径每轮最多 3 份详情，第二路最多 2 份。

完成标准：iteration-N.json 已写入唯一合法路径，两路查询、筛选和评分项都能回溯到当前需求版本；第 2 轮起的 `decision_basis` 已保留历史评分并记录本轮既定方向。文件写入成功后直接编译，不因为进入新的工具调用而重新评分、重算榜单或再次决定关键词。

### 8. 编译本轮搜索工作流

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" search --task-id TASK_ID --iteration N --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --plan-file "/ABSOLUTE/TASK_WORK_DIR/wts/search-plans/iteration-N.json"
```

Builder 会加载 assets/channel/*.json 和 assets/workflows/*.json，绑定猎聘 URL、页面识别、Selector、筛选交互、抽取 Schema 与硬筛谓词，保存不可变工作流后只返回短引用。Builder 校验 SearchPlan 失败时，按返回的错误原因修正同一个 iteration-N.json 并重新编译一次；仍失败则停止并说明。

Builder 同时计算 `decision_receipt` 的总分、推荐/强匹配人数与 Top 10，核对评分引用和 PRF 经历证据；它不代替 Agent 判断岗位匹配。输入仍用 `site_filters`、`decision_basis.candidate_scores`；输出的 `site_filter_fields`、`scores`、`counts`、`top10` 不能反填输入。编译成功后消费回执、输出对应播报，按返回的 `next_action` 使用已有 `workflow_ref` 执行。写入、编辑、编译成功只是机械衔接，不构成重做上一轮评分或决策的新证据。

### 9. 执行工作流

先输出播报节点 3，再只调用一次 browser_run_workflow(task_id, workflow_ref)。该工作流在模型外连续完成两路查询：搜索和站内筛选、卡片抽取（每路首屏最多 30 张）、卡片硬筛、卡片信号判定、只为 matched/unknown 且信号足够的卡片按详情预算采详情、详情硬筛和结果落盘。不要让 Agent 逐步调用 browser_click 或 browser_type 重演流程。

### 10. 读取结果

先检查运行结果的 status、error_code、summary.metrics、summary.sections 和显式业务 summary。对 success 或 partial 结果，用 browser_read_workflow_result 先读 details.primary，若有第二路再读 details.secondary，详情建议 limit=3（工具会自动缩小过长页面）；工具按内容长度分页，has_more=true 时用 next_offset 继续，不能直接加 limit。读过的详情保留用于评分，不重复读，也不要临时写脚本解析整份结果；字段为 null 代表未采集到，按 unknown 处理，不能当成字符串切片。partial 或任一路径 search.*.unsupported_filters 非空时必须再读 search，但不得仅因站内筛选降级而重跑同一轮。需要解释其他失败时再读 candidates 和 failures。success 且候选人数量为 0 是正常空结果，不是页面失败或登录失效。结果读完后输出播报节点 4；站内筛选降级时说明哪个条件未能确认生效。有 hard_filter_fallback 的条件继续由详情补筛；活跃度、跳槽频率没有自动硬筛回退，必须说明未验证，不能承诺候选人已满足。

### 11. 逐候选评分

仅对详情硬筛状态为 matched 或 unknown、且当前需求版本下尚未评分的候选人评分；跨轮按 candidate_ref 去重。当前由 Root 逐候选完成语义评估，没有独立并发评分器；每位候选人的判断只依据当前需求版本和这一份详情，不用其他人的分数或已播报人数倒推评分。

开始评分前先复用最近 `decision_basis` 中已完成的条目，只评当前版本尚未评分的人。每人记录三维原始分、硬冲突结论、unknown、简短证据说明及原始详情引用；不要只记人数或总分。新需求版本、新详情证据或可指出的事实/计算错误允许重评，但只修订受影响的条目并写 `correction_reason`；需要版本切换时所有保留候选人按新版本重评。不能为了维持已播报的数字调整分数。

评分步骤：

1. **硬冲突判定**。只有详情原文明确抵触某条明确的硬性筛选条件或排除信号，才构成硬冲突，必须引用原文。信息缺失、证据弱、能力差距、低分都不是硬冲突。有硬冲突 = **不符合**；没有 = **符合**。符合只是准入，不代表推荐。
2. **必须满足匹配分**（0–100）：对照必须满足与硬性筛选条件。90–100 高度匹配，80–89 强匹配，70–79 基本匹配，60–69 弱、存在实质缺口，低于 60 不推荐。
3. **加分项匹配分**（0–100）：需求版本里有加分项才评，否则记"不适用"。分段同上。
4. **风险分**（0–100）：需求版本里有排除信号才评，否则记"不适用"。0 无明确风险，1–29 低，30–59 实质，60–79 高，80–100 严重。
5. **总分** = 必须满足 × 60% + 加分项 × 25% + (100 − 风险) × 15%；不适用的维度剔除后按剩余权重重新归一化，四舍五入到整数。
6. 每条得分注明详情原文依据；找不到依据的硬条件记 **unknown**，不给分也不算否定，并在结果中逐项列出。

判定口径：**可推荐** = 符合且总分 ≥ 60。**强匹配** = 符合、总分 ≥ 80、必须满足 ≥ 70、风险不适用或 ≤ 30。**强池** = Top 10 已满且至少 5 位强匹配。

**Top 10 维护**：合并当前需求版本下历轮全部已评分候选人，按总分、必须满足分、candidate_ref 的顺序确定性重排，只展示前 10；退出榜单的候选人评分继续保留。继续下一轮时将原始评分随下一计划一并保存，播报节点 5 等待 Builder 的确定性计数，不在下一次工具前重新评一遍。

### 12. PRF：先试后晋升

每个支持词处于以下状态之一：**活跃词**（可进主路径）、**备用词**（救援时激活）、**待试词**（只能进下一次第二路）、**已拒绝**、**无法判定**。PRF 是产生待试词的唯一来源。

**提议**（每轮最多 1 个）：本轮已完成评分、没有现存待试词、未触发致命错误或未对账状态、且未到最大轮次时，执行：

- **种子**：榜单中符合、总分 ≥ 75、必须满足 ≥ 70、风险不适用或 ≤ 45 的候选人，按总分取前 5；不足 2 名则本轮不提议。
- **负样本**：本轮已评分中不符合或总分 < 60 的候选人。
- **候选短语**：在至少 2 位不同种子的 `work_experience_summary` 或 `project_experience_summary` 中逐字出现的技术、工具、框架、方法短语（"Flink CDC""LangGraph"），最多提出 4 个。`self_summary`、技能标签、标题不能充当种子经历证据，即使词相同。拒绝：已在关键词或已用词族中的、职责句、公司名、地点、学校、学历、薪资、泛词，以及本轮负样本文本中出现比例 ≥ 0.4 的。负样本匹配范围固定为详情中提取的经历、自评、技能、标题等文本字段，按候选人计数，包含自评；不要在不同工具之间切换检索口径。
- 接受第一个通过的短语，标为待试词，在 `prf_decision.evidence` 保存不同种子的 candidate_ref、来源字段和原文短引文。没有合格词明确记 `none`，判定拒绝记 `rejected` 并保存理由；这些是正常结果，下次工具继续复用，不再把它们当成未完成的思考。

**试用**：待试词只在下一轮第二路以 PRF 探针执行（步骤 7）。执行后先按运行结果对账，再裁决：

- 结果明确：该路带来 ≥ 1 名新增可推荐候选人，且没有明显噪音或方向漂移 → 晋升为活跃词，可进后续主路径；否则 → 已拒绝，不再使用。
- 证明未执行或未产生效果 → 保持待试，只有在下一轮重新编译执行后才再试。
- 效果未知 → 保持待试，暂停等待对账，不提议新词。
- 已确认执行但结果确定性不可评价（如详情全部失败或评分致命失败）→ 标为无法判定，终止本次寻访并保存证据。

已拒绝与无法判定不视为可重试失败。有待试词期间不提议新的 PRF 短语；救援步骤也不另外发起 PRF。

### 13. 反思（只有建议权）

反思和 Controller 是当前推理步骤，不是 Builder 子命令；Builder 只有 preflight、search、settle，不存在 reflect 或单独评分命令。

写一段不超过 5 句的反思：本轮两路各自的新增/重复情况；对现有活跃词和备用词提出激活 / 保留 / 降权 / 移除；对站内筛选字段提出保留 / 移除 / 新增（只限步骤 7 支持的字段，活跃度和跳槽频率仍须有用户确认）；如认为可以停止，给出理由。反思只提供证据与建议，不设第二套停止门槛；是否停止统一由步骤 14 判定。反思可以记录对待试词的观察，但不得提前晋升它，不造新词、不直接改词表、不指定下一条查询。

### 14. Controller 决策

Controller 是停止与下一轮关键词的最终决策者，按下列优先级判定：

1. 致命错误，或有外部副作用的动作效果未对账 → 终止或暂停，不报告终态。
2. 已达最大轮次（轮次预算与 5 的较小值）→ 硬停。
3. 没有任何可执行查询（活跃词、备用词、待试词、仅锚点查询都已用尽）→ 以"词族耗尽"异常终止。
4. 质量门：强匹配 ≥ 3 或已成强池 → 可停；但有新候选人的轮次不足 2 且仍有未试词族 → 继续。强匹配 < 3 时：有未试词族 → 继续；没有 → 先放宽一次（激活备用词或换相邻写法）再允许低质量停止。
5. 救援（决定继续但没有可选活跃词族时，按序执行一步）：激活备用词 → 试跑已存在的待试词 → 仅主锚点查询（最多一次）→ 以"词族耗尽"停止。

继续时：输出下一轮主路径关键词与非地点筛选调整，对上轮反思逐条表态（接受 / 部分接受 / 拒绝），回到步骤 7。停止时：记录确定性停止原因——强匹配足够、新增候选不足、多轮无进展、达到最大轮次、词族耗尽、预算。

继续时把本次决策写入下一计划的 `decision_basis.next_action`，编译成功后与评分回执合并播报节点 6；停止时进入步骤 15 结算并交付。决策不因已向用户预告下一轮而改变，明确的新证据或错误可以修订并简短说明。

### 15. 每轮小结与终态报告

每轮小结就是播报节点 6，1–3 句白话：这轮两组词各带来多少新人、多少是重复；累计可推荐和强匹配各几人；继续则说下一轮换哪组关键词及原因，停止则说一句原因并告知马上给出报告。待试词的晋升或拒绝、反思表态等内部记录留在决策记录里，不进小结。增量效果按新增可推荐候选人数描述，停止条件仍以步骤 14 为准。

停止后复用已记录评分，只补本轮新候选人的完整评估；不要为写报告重评历史候选人，也不要为了凑满 Top 10 改变原评分。按 [最后一轮结算](references/search-plan.md#最后一轮结算) 保存 `<TASK_WORK_DIR>/wts/final-decision.json`：只存完整 decision_basis，completed_iteration=N，next_action 仅含 action=report 和 reason。然后执行：

```text
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts/scripts/build_workflow.py" settle --task-id TASK_ID --iteration N --task-work-dir "/ABSOLUTE/TASK_WORK_DIR"
```

N 是最后已完成的搜索轮次（1–5），不是 N+1；不用创建 iteration-6.json。Builder 自动读取 iteration-N.json 和 final-decision.json，基于已执行计划快照结算，返回 `report_data_file`（`wts/final-report-data.json`）。读取该文件中的 Top 10 姓名、真实 detail_url、分数、证据、unknown 后直接按以下模板交付；无需扫描结果目录补链接。链接为 null 时写明缺失。该模式不编译或执行额外搜索。

```text
# 寻访报告（需求版本 vN）

【结果】Top 10：候选人 · 符合/不符合 · 总分（必须 / 加分 / 风险）· 一句话依据 · 硬条件 unknown 项 · [查看猎聘详情](detail_url)
【搜索覆盖】共 X 轮 Y 个查询（主路径 a / 第二路 b）；见到 Z 名、新增 M 名、可推荐 P 名、强匹配 Q 名；晋升 / 拒绝的待试词；站内筛选降级项
【停止原因】一条确定性原因
【未满足原因】距目标人数差多少、哪些词族已耗尽、哪些硬条件无法验证
【失败项】详情采集失败或没有 detail_url 的候选人及原因
```

每位候选人必须提供真实的 [查看猎聘详情](detail_url)；不得把 candidate_ref 或内部定位信息当成网址。数字不得虚构。

## 决策规则

- 只有 JD 明确要求且渠道数据能够验证的条件才进入 hard_filters。语义匹配、潜力和偏好留给评分。
- 明确且受 hard_filters 支持的硬条件即使已放进 site_filters，仍必须保留在 hard_filters；站内筛选不等于最终证明。活跃度、跳槽频率当前只支持站内预设，生效失败时报告未验证，不伪造本地硬筛结果。
- 卡片硬筛只淘汰存在明确反证的人（目标为工程岗而卡片头衔为零售、销售且没有任何工程信号）。卡片未展示关键词、院校标签或其他可能折叠的字段时标记 unknown，继续采详情。卡片信号不足只是暂缓采详情，不是淘汰。
- 详情硬筛是最终确定性准入。字段缺失仍为 unknown，不得自动当作不符合。
- 年龄、性别仅可作为站内筛选缩小召回范围（`site_filters.age_range`、`site_filters.gender`），不得写入 `hard_filters`，也不参与评分、排序或硬冲突判定；它们没有本地硬筛回退，页面操作失败时按 `unsupported_filters` 报告未验证，不得当作已满足。学校名称、民族、婚育仍完全不参与检索、站内筛选、评分、排序或硬冲突判定，用户提出时说明不予执行，其余条件照常处理。
- 所有站内筛选操作失败时都继续后续搜索，并从 search.unsupported_filters 读取失败字段、请求值和错误原因。站内筛选只是缩小召回范围；同字段硬条件仍由后续卡片和详情 data.filter 执行。结果状态为 partial 时应说明筛选降级，不要再用全局 allow_partial_filters 控制该策略。
- 零结果是有效的查询结果，进入正常的评分、反思和 Controller 决策；工具错误、超时或页面失败是失败，不记作零结果。
- 未被站内筛选容错块捕获的 TARGET_NOT_FOUND、WAIT_TIMEOUT、PAGE_STATE_NOT_RECOGNIZED，或工作流引用失效时停止当前轮，不得原样重跑同一个 workflow_ref，也不要让 Agent 临时拼装 Workflow。只有调整搜索计划、更新 Skill 页面规则或恢复明确的人工作业状态后，才能重新编译执行。
- 有外部副作用的动作出现网络错误、超时或效果未知时，先读取运行结果对账：已有明确观察则消费结果、不重试；证明未产生效果后才允许在下一轮重新编译执行；仍无法确定时暂停并说明，不报告完成。
- 任何停止、暂停或等待用户处理的状态都要先按进度播报的异常格式告知用户，再停下；不能只留下一次失败的工具调用。
- 只有前置或搜索 Workflow 明确返回 login_required 时才能判断未登录；其他页面错误不得推断为登录失效。
- 详情采集失败或没有 detail_url 时，将其放入失败项并明确说明，不得伪造 URL。

## 资源与工具边界

- assets/channel/liepin.json：域名、URL、页面识别、Selector、筛选控件、取值映射和预算。
- assets/channel/*-extraction.json：卡片与详情的声明式抽取 Schema。
- assets/workflows/*.json：前置检测、搜索和详情工作流模板。
- scripts/build_workflow.py：校验 SearchPlan、生成通用硬筛谓词、展开模板、计算摘要并原子保存工作流。
- scripts/decision_basis.py：复用评分与决策的校验和确定性回执，由 Builder 调用，不单独触发模型或浏览器。

Skill 不连接浏览器、不读 Cookie、不发送 WS/IPC、不执行任意 JavaScript。Agent 只接触 workflow_ref 和 result_ref。
