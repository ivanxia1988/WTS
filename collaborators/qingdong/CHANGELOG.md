### 2026-09-22 · 去掉探测，硬筛不够就补搜；播报只说猎头句

#### 改了什么

- 删除登录后的公司探测（步骤 6.5、`probe` 子命令与资产）。确认目标公司后直接带公司词搜。
- 公司池状态改为未用 / 已用 / 人不够。选择顺序：自定义 → 调研推荐序 → 扩充命中人数。
- 主路径带公司词且硬筛后可采人数不足上限时，先采集已有的人，本轮再 `refill` 去掉该公司词补搜，采集差额。每轮一次，不计入轮次。
- 播报改成猎头句：改计划、编译失败那一轮对用户不出字。
- collect 示例与 Builder 对齐：第 1 轮只写 `primary`；没有第二路时 `"secondary": []` 与省略同等。

#### 为什么改

- 探测只数卡片、不做硬筛，占一次浏览器往返却回答不了「够不够采满」。
- collect 示例带了 `"secondary": []`，第 1 轮编译失败后，主 Agent 把字段名讲给了猎头。

#### 需要重点测试

- 第 1 轮 collect 只写 `primary`，以及误写 `"secondary": []`，都能编译。
- 带公司词、硬筛后 2 人：先采集这 2 人，补搜后最多再采 3 人；池子该公司为「人不够」；只评一次。
- 硬筛已满 5 人：不写 refill。
- 无公司词或公司是硬条件：不写 refill。
- 登录后不再出现 probe 工作流。
- 补搜和改计划时用户侧看不到 collect、secondary、refill、workflow_ref。

### 2026-09-22 · 学历下限不再只点同一档

#### 改了什么

- 猎聘学历选项只含这一档。下限是本科及以下时，站内不点学历，页面留在不限；硬筛仍写下限及其以上每一档。下限是硕士时，站内点「硕士」和「博士/博士后」。下限是博士时只点「博士/博士后」。用户写明只要某一档时，站内和硬筛都只留那一档。

### 2026-09-22 · 第 1 轮评分后确认尺度

#### 改了什么

- 第 1 轮评分之后、扩张之前问一次「这个尺度对吗？」。用卡片和推荐理由给 2 位值得推荐、1 位不推荐的匿名样例。尺度对就继续；用户点名改某一条时写新需求版本，当轮重评后再判断扩张。第 2 轮起不问。本轮没评到人则跳过。

### 2026-09-22 · 一次澄清、市场求证、结束只留方向

#### 改了什么

- **澄清**：已触发的主题放进同一次提问。JD 已写清的跳过。只有答案引出新缺口才再问一次。选公司和确认画像仍在其后。
- **市场观察**：写之前派市场求证子 Agent，最多 6 次网络搜索。猎聘人数用本次结果，公开判断带来源。规则在 `references/market-research.md`。
- **结束选项**：去掉「以人找岗」。只保留换方向和「先到这里」。

### 2026-09-22 · 播报只说口语

#### 改了什么

- 「播报」去掉固定填空句。对用户自由说三件事：做完什么、多少人、下一步。搜索词直接说出，评价用「很匹配」「值得推荐」。`decision_basis`、Controller、主锚点、证据文本和工具提示留在文件里；改好了不向用户解释。

### 2026-09-22 · 主 Agent 不读采集详情；年龄单独走年限

#### 改了什么

- `seen-and-expand.md`：采集完成后用 `score_inputs.py` 的索引追加台账，`profile_path` 交给评分子 Agent。
- 决策规则：年龄要求写成估成年限并写入 `experience_years`。性别、学校名称、民族、婚育仍说明不予执行。

### 2026-09-21 · PRF 与反思改为子 Agent

#### 改了什么

- **步骤 12 / 13**：主 Agent 只传 `prf.md` / `reflect.md` 路径和材料，消费返回的 `prf_decision` 与反思 JSON。PRF 子 Agent 读详情文件，从高分简历经历原文抽待试词并裁决；评分不再代出 `prf_proposal`。
- 年龄确认绑在「城市与硬边界」主题，去掉「第 4 轮」这种会让人以为要先空跑前三轮的写法。

#### 为什么改

- 把 PRF 裁决和反思移出主上下文，主 Agent 只做 Controller。
- 「第 4 轮」是澄清主题序号，不是检索轮次，也不是「前面三轮不做」。

### 2026-09-21 · 评分改为单次子 Agent，主 Agent 不读简历和量表

#### 改了什么

- **评分子 Agent 一次评完**（步骤 11、`references/scoring.md`）：本轮只派一个评分子 Agent。子 Agent 上下文 = 当前需求（JD）、本轮待评人详情、`scoring.md`。一次返回 `{candidate_scores, labels, company_hits}`。
- **主 Agent 上下文**：只消费卡片、索引、上述返回值和 Builder 回执。`scoring.md` 从主 Agent 参考列表拿掉；公司池扩充用 `company_hits`。

#### 为什么改

- 当前宿主一次只能跑一个子 Agent，按人派发会串成多次等待。
- 简历全文和评分规则进主上下文会占窗口，也让主 Agent 自己改分；隔离后主 Agent 只拿分数和推荐理由。

### 2026-09-21 · 年龄要求估算为工作年限

#### 改了什么

- **年龄→年限估算**（步骤 2、3、决策规则、`references/search-plan.md`）：JD 或用户提出年龄要求时，不得拒绝或丢弃。按中国大陆常见入职年龄（本科 22 / 大专 21 / 硕士 25 / 博士 28）估成 `experience_years`，第 4 轮请用户确认后写入硬筛。年龄本身仍不进检索、筛选、评分，也不写 `age_range`。
- 候选人侧年限仍按简历工作或项目起止时间计算，重叠只计一次；不得用候选人年龄或毕业年份反推年限。

#### 为什么改

- 大模型常把年龄要求直接拒绝映射，中国大陆岗位又普遍写年龄；估成年限才能把业务意图落到猎聘能筛、简历能验证的条件上。

### 2026-09-21 · 已看台账、跨轮/跨任务去重、轮内扩张

基线：`WTS/source/` 于 origin/main `dda38ba`（Builder 0.5.2）。`source/` 是在该基线上修改后的完整 Skill 包，Builder 版本标识改为 `0.6.1`。

#### 改了什么

- **评分取证**：允许引用简历其他区块的明确原文；必须满足项尚未核实时保留推荐资格，但不计为强匹配，Builder 同步校验。

- **独立并行评分**：每份简历由子 Agent 读取已确认需求、原评分规则和单人详情文件后评分，主 Agent 汇总；脚本只返回文件索引，减少全文进入主上下文。评分量表与 Builder 校验不变。

- **已看台账 `wts/seen.json`**（新 `references/seen-and-expand.md`）：步骤 10 读完结果后把 details 和 failures 里的每个人追加进台账；它是"详情已打开"的唯一事实来源。步骤 15 把台账路径写进 `report.json.seen_ledger_path`；步骤 1 在用户选了备选方向发起新任务时合并上一次的台账。
- **先读卡片，再采详情**：search 只返回卡片，Agent 对照台账去重后提交 collect 名单。常规上限仍为 5＋3，轮内扩张保留；不再使用宿主不支持的排除操作。
- **轮内扩张（新步骤 11.5，新 Builder 子命令 `expand`）**：每轮详情数量不变；本轮评分后若达到**扩张门**（`references/scoring.md`：本轮新人可推荐占比 ≥ 50% 或新增强匹配 ≥ 2，且未成强池），就留在本轮从同一页再挑一批人打开，而不是进下一轮。挑谁、挑几个由 Agent 根据规则初筛后的卡片信息自行判断，不规定数量（建议：不全开，挑认为比较可能的，优先与本轮高分候选人相似的；Builder 只设一次最多 30 人的技术上限），写 `iteration-N-expand-K.json`，字段 `query` + `include_candidate_refs` + 照抄本轮的筛选和评分项。Builder 编译为卡片谓词 `selected_candidate`（只保留名单内的卡片，详情预算 = 名单长度），并校验 query 必须是本轮已执行的查询之一、hard_filters / semantic_criteria 与已执行计划一致。同一轮最多 3 次，扩张不计入轮次。
- **结果分区新增 `details.expand`**；`decision_basis.py` 的 `detail_section` 放开为 primary / secondary / expand，`candidate_scores` 上限从 25 提到 120（三轮加扩张会超过 25），计划文件和最终评分快照上限从 64 KiB 提到 256 KiB。
- **`executed_plan` 跳过扩张工作流**：扩张工作流带 `expansion=K` 标记，下一轮和 settle 找回本轮计划时忽略它，避免把扩张计划当成本轮搜索计划。
- **终态报告**（`references/final-report.md`）：`coverage` 新增 `expansions` 和 `skipped_seen`；新增 `not_recommended`（看过但没推荐的人数与原因聚合），推荐人选以 Markdown 表格展示概况、推荐程度、评分、依据、待核实项和详情链接；未推荐者只汇总数量和原因。

#### 同批次的策略与可读性改动（只改 SKILL.md 和 references，不涉及 Builder）

- **简历可见性测试与面试核实项**（步骤 2、`requirements-draft.md`、`scoring.md`、`final-report.md`）：通过反事实测试的每条要求再问"猎聘详情的哪个区块能看出来"，答不出来的（顶会论文、绩效、口碑、抗压等）进新桶 `verify_in_interview`，不删除、不评分、不筛选，画像和终态报告里单列提醒用户面试核实。必须满足分只按有证据的条目算，unknown 从分母剔除。
- **岗位经验澄清**：确认岗位实际需要的经验、职级或薪资条件；年限按简历实际经历计算，重叠时段只计一次，信息不足待核实。删除年龄映射年限的示例，避免把年限作为年龄筛选的替代。
- **播报可读性**（"播报"一节）：列出禁止出现在用户面前的内部名词清单（decision_basis、candidate_ref、PRF、Controller、Builder、证据文本、主锚点等）和白话对照表（主锚点→核心岗位词、强匹配→很匹配……）；Builder/宿主返回的校验提示一律不直接播报，修好就不提；轮次小结改为三句固定填空，杜绝"决策要求不至少"这类残句。
- **沿用旧评分逐字复制**（步骤 11）：carry-forward 上一轮 candidate_scores 时不润色 evidence_summary 等字段，Builder 提示"视为修订"时恢复原文再编译，不向用户解释。

#### 为什么改

- 顶会等简历不会写的条件被放进评分后，要么把人误杀，要么被模型自作主张删掉；现在给它一个明确去处。
- 年龄无法可靠推算工作年限；澄清实际岗位需要后，按可核实的经历判断。
- 用户反馈看不懂"证据文本""决策要求不至少""主锚点"，根因是内部名词和工具提示直接漏到了播报里。
- 现有工作流按列表顺序取前 5 / 前 3 张卡片开详情，第 2 轮的前几张往往就是第 1 轮开过的人；同一对话里第二次寻访更是完全不知道第一次看过谁。
- 猎聘首屏 30 张卡片，规则初筛后常剩二十多张；一轮只看 5 个，效果好的时候没有办法在同一页继续深挖，只能换词进下一轮。

#### 对宿主的假设（未验证，用不了再改）

- 扩张工作流沿用 `candidate.search` 的 `workflow_type` 和能力声明，只多一个顶层 `expansion` 字段；宿主若拒绝未知顶层字段需要放行。

#### 需要重点测试

1. Agent 是否在 collect 前按台账排除已看的人，并避免主、次路径重复选人。
2. 扩张：编译是否通过、`details.expand` 是否只含名单内的人、扩张评出的人能否顺利进入下一轮 `decision_basis` 和 settle。
3. 选备选方向发起第二次寻访时，台账是否被合并、第一次看过的人是否被跳过。
4. 一轮内连续扩张两三次后，猎聘是否触发"操作频繁"；台账里当天累计打开数的上限（默认 60）是否合适。
