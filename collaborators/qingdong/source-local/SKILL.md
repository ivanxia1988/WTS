# 本地简历库智能寻访

候选人来自宿主工具 `search_local_resumes` 查询的本机简历索引，不经过浏览器，也不访问任何招聘网站。检索、硬筛、评分和 PRF 由**检索子 Agent** 完成；主 Agent 只读它的回执，不读简历正文。**网络搜索工具**只在步骤 4 调研目标公司和步骤 13 市场求证时使用。

## 与用户交互

### 提问

request_user_input 是**独占调用**：它所在的这一轮里没有别的工具调用。固定 skill_name=wts-local，step_id 见各步。宿主的字段约束：每题最多 8 个选项；label ≤ 80 字，只放选项本身，理由和差异写在 description（≤ 240 字）；prompt ≤ 300 字；用户可自行填写用 allow_custom=true 表达，推荐的填写值放 custom_placeholder。确认需求时，完整需求稿放在问题的 description；如果超过字段限制，先作为普通文本完整输出，description 只放摘要。prompt 始终只写一句简短问题，不重复正文。

**每次让用户选，都给推荐**——推荐统一写在 label 开头：`[推荐] 选项内容`；所有选项的 `recommended` 字段保持 false（宿主的推荐标记每题只允许一个，且会和前缀重复，所以只用前缀）。单选：一项带 [推荐]。多选：前 3 项带 [推荐]（不足 3 个可选项时全标），按推荐顺序排列。自由填写：custom_placeholder 给推荐值。每个推荐在 description 里附一句依据，推荐就是 Agent 自己判断的公开版本，让用户多数时候只需同意。

**用户看到的一律是白话**：选项、画像、播报、报告都写给猎头看。Agent 的规格和记录（需求确认稿、检索计划、回执、内部报告）写到任务工作目录 `<TASK_WORK_DIR>/wts-local/` 下的文件里，给用户的文本是从文件渲染出来的视图；title 范围、公司层、置信度、candidate_ref 等内部字段只在文件和决策记录里出现。

新建文件使用 `write_file`；修正已经存在的需求、计划或决策文件使用 `edit_file`。不要用临时脚本绕过字段校验或回改已经执行的历史计划。

### 播报

检索阶段用户只能看到一连串工具调用。用户看见的句子是**猎头句**：另一位猎头听得懂的 1–3 句，只讲用了哪些词、多少人条件对得上、接下来多看几份或换哪家公司。评价说「很匹配」「值得推荐」。姓名、分数、公司、简历内容只在终态报告出现。步骤 9 的判断样例按该步写给用户看。播报不占独占调用。

猎头句用中文写。岗位词、技术名词、公司名保持原文，句子主干是中文。

完成标准：每一句去掉任务目录和工具名之后，仍能单独讲给猎头听；句子主干是中文。

只在标了 **播报** 的节点说话。校验失败、改计划、漏写字段：改对并能通过校验，这一轮不对用户输出任何字。简历库状态需要用户动手时才开口，口径见步骤 8。

## 检索子 Agent

宿主以工具方式派子 Agent：一次只能派一个，派出后主 Agent 阻塞到它返回，每次往返都很慢。所以子 Agent 是**稀缺调用**，只在四个节点派：步骤 7 每轮一次、步骤 9 改尺度后重评一次、步骤 10 每次扩张一次、步骤 5 检索中途换需求版本后重评一次。

每次派发都走同一个接口：

1. 主 Agent 用 `write_file` 写**任务单** `<TASK_WORK_DIR>/wts-local/briefs/<运行名>.json`，字段见 `references/retrieval.md`。
2. 派子 Agent，任务说明只写一句：「读 `<内置 Skill 目录>/wts-local/references/retrieval.md`，按任务单 `<任务单绝对路径>` 执行。」
3. 子 Agent 把结果写进任务单指定的 run 文件后返回。主 Agent 不读 run 文件，只运行：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts-local/scripts/ledger.py" merge --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --run-file "/ABSOLUTE/TASK_WORK_DIR/wts-local/runs/<运行名>.json"
```

脚本把 run 文件并入已看台账和评分表，重算总分、`labels`、Top 10、强池和扩张门，打印**回执**。后续判断都用回执里的数字。merge 报错时按错误原因改任务单，再派一次同一运行；第二次仍报错则停止并说明。

运行名：常规轮 `iteration-N`，扩张 `iteration-N-expand-K`，重评 `iteration-N-rescore-K`（N 取最近一次已开始的轮次，第 1 轮开始前为 0）。

## 执行 SOP

### 1. 取上下文

从任务上下文取得 JD、职位标题（可能缺失）、目标人数、任务 ID、绝对的任务工作目录、绝对的内置 Skill 目录和轮次预算，直接使用运行时提供的绝对路径。用户在输入里指定了简历目录或文件类型（只查 Excel 台账、只查 PDF 简历）时照录，步骤 6 写进计划；没有指定就不写，路径不自行猜测。

用户在上一次寻访报告后选择了某个备选方向再发起本次任务时，对话历史里会有那个方向的名称和 title 范围：它就是本次的主池，其余全部从零开始——重新拆解、重新澄清、重新确认。唯一延续的是**已看台账**：对话历史里有上一次报告的 `seen_ledger_path` 时运行：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts-local/scripts/ledger.py" adopt --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --previous-ledger "<seen_ledger_path>"
```

这些人本次不再评。

### 2. 拆解需求，形成需求确认稿草案

- **标题锚点**：有职位标题时，从标题提取 1–2 个候选人会在简历里逐字写出的短锚点，去掉"工程师""开发""研发""算法""技术专家"等后缀和公司前缀（"千问-AI Agent工程师"→"AI Agent"；"Flink开发工程师"→"Flink"）。没有标题时从 JD 总结一个岗位锚点并标注"[由 JD 总结]"。第一个锚点是**主锚点**，全程固定出现在每条查询里；第二个是**第二锚点**，只作第 1 轮的搭配词。
- **原子化**：JD 是"尚未验证的需求证据"，逐句拆成独立需求。缺失的写"未指定"并保持未指定直到用户回答；推测标 [假设]。缺失、推测和下面三种病症都汇入待澄清清单，按步骤 3 的主题归类。示例——"需要很强的数据能力，北京上海深圳杭州成都均可"：正确拆法是"数据能力是工程/分析/建模哪种？未指定"、"五个城市是工作地还是来源地？未指定"，两条都进待澄清清单。
- **JD 病症**：很多 JD 是从网上抄来再改的，三种常见病识别后打标记，提问在步骤 3 的对应主题：
  - **[CONFLICT] 逻辑矛盾**：两条要求在逻辑上不能同时成立（"3 年以上经验"+"资深架构师职级"；"本科"+"博士优先"；"10 年以上"+"30 岁以下"）。性别、学校名称、民族、婚育一方按决策规则直接告知不执行，矛盾随之消失；年龄先标 [年龄→年限]。
  - **[过载] 全能型 JD**：每条单看合理，合起来市场上没有人。信号：反事实测试后必须满足仍 > 5 条；必须满足横跨 ≥ 3 个职能；年限与职级明显不配。
  - **[套话] 模板句**：沟通能力、团队合作、责任心、抗压这类通用句。先试着改写成可观察行为（"跨团队推动项目落地"→ 看项目经历里有无跨部门项目）；改不动的标 [套话]，列入确认稿【备注】供用户捡回。
- **[假设] 的去向**：每个 [假设] 走两条路之一——在澄清轮里问掉，或原样列进确认稿【关键判断】让用户看见。
- **必须满足 / 加分项 / 排除信号**——按用途分类：
  - 必须满足：缺了就做不成岗位，用于检索和硬筛。判据是**反事实测试**："不满足此条但其余都优秀的人，能否六个月内做成岗位？"答"可能"就降为加分项。重点审查学历、年限、知名公司是否只是能力的代理变量。每条注来源（JD 第 n 条 / 用户确认）。
  - **简历可见性测试**：通过反事实测试的每一条，再问"简历的哪一段能看出来？"（工作经历 / 项目经历 / 技能 / 教育经历 / 自我评价）。答得出来的才留在必须满足或加分项，并记下区块。答不出来的——顶会论文、绩效、口碑、抗压、带团队规模这类简历通常不写的——不删除，进 **面试核实项**（`verify_in_interview`），确认稿和画像里单列一行。这些条不写入必须满足、加分项或排除信号。
  - 加分项：确实正确但只进评分。
  - 排除信号：硬过滤。来源：JD 明确不要、用户补充不要、默认排除。默认排除"近 1 年内多次跳槽"，确认稿中标"默认"，用户可要求去掉。JD 或用户信息明确招聘公司时，记录公司名及依据，加入"当前仍在该公司任职"；曾经任职不排除。仅有推测时在现有澄清环节确认，无法确认则不启用。
  - 模糊素质词按 [套话] 处理。
- **硬性筛选条件**：只收 JD 明确写出、且简历正文能验证的地点、学历、工作年限、公司、学校类型、工作内容。未声明的默认"不限"；年限、学历、薪资未填写时同样默认不限，是否该成为必须满足由反事实测试决定，需要裁决时归入同一次澄清的城市与硬边界。JD 里的学历是下限：写「本科」即本科及以上，写「硕士」即硕士及以上。确认稿的 `education` 写下限这一档；用户写明只要这一档、不要更高时，才记下「只要这一档」。硬筛怎么写见 `references/search-plan.md`。
- **检索关键词**：检索工具只认字面词、以空格分词，所以每个检索词都是简历里会逐字出现、**不含空格**的原子词。从 JD 提取最多 8 个非锚点**支持词**——技术、工具、框架、算法、方法、稳定的能力名词（"大模型应用落地"不取，"RAG""LangChain"取；"高并发系统建设"→"高并发"）。同一概念的不同写法归为一个**词族**，一个词族只取一个代表词。前 6 个为**活跃词**，其余为**备用词**。锚点本身含空格时（"AI Agent"）检索时按空格拆成几个词，全部算锚点。公司名是另一类检索词——**公司词**——由步骤 4 单独产生和管理，与支持词互不占额。
- **不做搜索词**：薪资、地点政策、流程偏好、抽象素质、受保护属性。它们分别只进硬性筛选、评分项，或完全不用。
- **年龄要求**：JD 或用户提到年龄要求（含"35 岁以下""最好不超过 30""年轻一些"）时，标 [年龄→年限]，进待澄清清单。估算、提问和写入见步骤 3 的年龄转换专项。

完成标准：主锚点、必须满足、硬性筛选条件、检索关键词四项都有明确内容或明确写着"未指定"；面试核实项已单列；待澄清清单已列出全部"未指定"、[假设]、[CONFLICT]、[过载]、[年龄→年限]，并按步骤 3 的主题归好类；[套话] 已单列。

### 3. 判断是否需要澄清

有效检索计划至少要有一个明确的主锚点，加上至少一个能区分候选人范围的支持词或硬性筛选条件。仅有"产品经理""技术人员""运营"等宽泛岗位名，加"有技术意识""学习能力强"等软性特质，不算有效搜索锚点；软性特质按 [套话] 处理。

**门禁**——五类必答：岗位与职级、核心技能、必须满足的边界、城市、排除信号。每一类都要有结论（JD 写清了算有，用户答了算有）且没有未裁决的 [CONFLICT]，才进需求确认门。目标公司走步骤 4，在此不问。另外三种情形无论如何都要问：任务上下文只有职位 ID/名称而没有 JD 正文；只有宽泛岗位名和软性特质；同一描述存在多个会显著改变关键词或硬性筛选条件的合理解释。

**一次澄清**——下表里已触发的主题放进同一次 request_user_input，step_id=clarify-jd。JD 已写清的主题不出现。同一缺口只问一次。宿主一次可以确认多题，不要拆成多轮。

| 主题 | 触发条件 | 题型 |
| --- | --- | --- |
| 岗位定位 | 主锚点不清，或有多种解释 | 单选 + 自定义 |
| 必须满足的裁决 | 有 [过载]，或反事实测试降级了任何一条 | 多选：Agent 给出必须满足名单与降级名单，用户勾选"缺了就不行"的 |
| 矛盾裁决 | 有 [CONFLICT] | 每条三选一：取前者 / 取后者 / 都放宽为加分 |
| 城市与硬边界 | 城市未指定、多城市，年限/学历是否算硬条件待定，或有 [年龄→年限] | 城市自由填写；硬边界单选；年龄转换单选（见下） |
| 排除信号 | JD 没写"不要什么" | 多选 + 默认项 + 自定义 |

城市专项：实际工作地 ≠ 候选人来源地。JD 出现多个城市要问清几个 HC、最终在哪入职、"均可"是各地有团队还是接受搬迁；JD 列出几十个城市时问"是否有重点城市、真实主阵地在哪"。

年龄转换专项：有 [年龄→年限] 时，在同一次澄清里请用户确认估算年限。先估出年限再写进选项。

- 入职年龄：学历未写或本科按 22，大专 21，硕士 25，博士 28。
- 年限 = 年龄 − 入职年龄，结果小于 0 记 0。"A 岁以下"只写 max；"A 岁以上"只写 min；"A–B 岁"两边都写。写不出数字的模糊说法（"年轻""不能太大"）不编数字，仍标 [年龄→年限]。
- 例：35 岁以下+本科 → 13 年以内；30 岁以下+本科 → 8 年以内；25–35 岁+本科 → 3–13 年；40 岁以上+本科 → 18 年以上。
- JD 已写年限则先用年限；估出的年限与已有年限不能同时成立时标 [CONFLICT]，走矛盾裁决。

选项固定四个：[推荐] 工作年限（label 写估算结果，如"13 年以内"）、职级/带团队范围、薪资带宽、不设这项限制。用户选年限或自定义年限后写入 `experience_years`，不写年龄字段，来源标"用户确认（由年龄估算年限）"，精确范围进硬性筛选；选职级或薪资则分别进评分项；选不设则年限保持不限。

收到答案后合并一次。只有答案引出新缺口才再问一次。仍不足以形成有效搜索词时停止并说明缺少什么。

完成标准：五类门禁全部有结论；待澄清清单里没有未处理的 [CONFLICT] 和 [过载]；剩余 [假设] 已标记为待进【关键判断】。

### 4. 目标公司

城市已确认之后才做这一步，因为调研要按城市找公司。两个分支：

- **JD 已列出目标公司**：照录，每家置信度 1.0，来源标"JD"，跳过调研和提问。
- **JD 未列出**：先用一句白话告知用户（"JD 没有指定目标公司，我先用网络搜索调研一下，再请您确认"），再按 `references/target-company-research.md` 用网络搜索工具调研，产出岗位定位、公司类别和带置信度的公司清单，然后按其提问格式调用 request_user_input，step_id=confirm-target-companies。用户自定义补充的公司置信度 1.0，来源标"用户"；用户勾选调研结果只表示采纳，置信度保持调研值。

**去向**：

- **目标公司**：用户采纳的公司（勾选的调研结果 + 自定义补充）→ 进**目标公司池**，同时进加分项和市场洞察。置信度只用于排序和记录。
- **公司类别**：调研得到的类别本身，写方向不列名 → 进市场洞察。

**目标公司池**是贯穿全程的公司词候选清单，记在决策记录里，每家一行：公司名｜来源｜置信度或命中人数｜未用 / 已用 / 人不够。两个来源：

- **初始**：本步骤的目标公司。用户自定义补充的排最前（按填写顺序），其后是勾选的调研公司，按推荐顺序。全部直接标**未用**。
- **扩充**：第 1 轮起，每次回执的 `company_hits` 并入池子，来源标"高分候选人"，记命中人数；已在池中的公司累加命中人数。这是第 1 轮之后新公司的唯一来源；扩充公司只作公司词和市场洞察，加分项只认初始目标公司。

**公司词**的全部使用规则集中在此：

- 已确认的招聘公司不进入目标公司池，也不从候选人履历中重新加入；按已确认的全称或简称识别，不自行扩大到集团或关联公司。
- 公司词写成简历里最常出现的不含空格的写法（"阿里巴巴""字节跳动"）。
- 每轮主路径最多带一个公司词，一家公司只用一次；第二路永远只有锚点和支持词。选择顺序：未用的自定义公司按填写顺序 → 未用的调研公司按推荐顺序 → 未用的扩充公司按命中人数。反思提建议，Controller 拍板。没有未用的候选时主路径只用锚点和支持词。
- 用过且回执 `refill` 为空 → **已用**；回执 `refill` 非空 → **人不够**。已用和人不够都不再选。
- 公司词是检索词而非硬条件——公司进 hard_filters 的唯一途径仍是 JD 或用户明确要求"只要这些公司"。

用户全部不选或选"不限"时目标公司写"不限"，池子初始为空，主路径可以不带公司词；第 2 轮起仍按高分候选人扩充；调研得到的岗位定位和公司类别保留给市场洞察。

完成标准：目标公司有明确结论（清单或"不限"）；每家公司有置信度和来源；目标公司池已按推荐顺序建好。

### 5. 需求确认门

写确认稿之前先完成两件事：

- **城市分层**：城市 A=实际工作地/主池，B=可搬迁来源，C=仅观察不入池。
- **主池与备选方向**：**主池**是 Agent 判断最可能的方向 = 精确 title × 目标公司 × 城市 A 层，是本次 1–3 轮检索唯一服务的对象。**备选方向**是 Agent 判断"不是最可能、但也有可能"的其他解释——相邻 title、相邻行业、可迁移背景、B 层城市的组合——最多 2 个，每个一行写清名称、title 范围、与主池的差别。备选方向只记在决策记录里，在步骤 14 呈现；确认稿只写主池。主池拿不准时把它当作待澄清项在步骤 3 问。

然后按 `references/requirements-draft.md`：把需求确认稿写成 `<TASK_WORK_DIR>/wts-local/requirements/vN.json`，从它渲染**候选人画像**，做完决策无损核对后先以普通文本输出画像，再调用 request_user_input，step_id=confirm-requirements，prompt 一句"这是我理解的候选人画像，可以开始找了吗？"，选项两个："[推荐] 确认，开始找人" / "我要改某一处"（allow_custom，填写改哪里）。用户看到的只有画像；确认稿是 Agent 的规格，只存在于文件里。

用户选"我要改某一处"或在自定义里质疑某处时，只改确认稿被质疑的部分，写新版本文件，重新渲染完整画像再次请求确认。"没有补充""OK 吧"这类含糊回复视为未确认，同样重新呈现再问一次。

检索开始后用户补充需求时：写新版本文件，只在当前轮结束、下一轮检索计划编写前生效；纯约束型补充（如新增地点限制）只更新硬性筛选条件和评分项；版本切换后派一次重评（`mode=rescore`，重评全部已评的人，`prf=false`），用回执重建榜单。步骤 9 的尺度调整当轮生效，见该步。

完成标准：用户选了"确认，开始找人"，该版本文件冻结为当前需求版本；画像里每条必须满足、硬性条件、排除信号、关键判断都能在文件里找到对应。

**播报**："需求已确认，开始在本地简历库里找第 1 轮。"

### 6. 编写第 N 轮检索计划

读当前需求版本文件（`<TASK_WORK_DIR>/wts-local/requirements/` 下 N 最大的 vN.json）和 `references/search-plan.md` 的字段契约，把需求版本拆为两路查询、硬性条件和语义评分项，写入 `<TASK_WORK_DIR>/wts-local/search-plans/iteration-N.json`。所有查询都是**与查询**：每个词都必须在简历里出现。

- **主路径查询（利用）**：第 1 轮的起手形态 = 主锚点 + 2 个不同词族的支持词 + 1 个公司词（按步骤 4 的规则选，没有则省去）。支持词里第二锚点算一个，其余优先核心技能、框架工具而非泛领域词；选哪两个由 Agent 判断。第 2 轮起形态由 Agent 按上一轮结果调：召回少就减到 1 个支持词或换公司词，召回多而噪音大就保留 2 个；支持词从活跃词中取不同词族，优先沿用带来新可推荐候选人的组合。
- **第二路查询（探索）**：第 2 轮起才有。有待试词时 = 主锚点 + 该待试词（**PRF 探针**）；否则 = 主锚点 + 1 个未试词族的支持词，优先级最高的备用词优先（**通用探索**）；两者都没有则本轮只有主路径。
- 一条查询内词族不重复；第二路与主路径本轮的非锚点词族不同；已发出过的词组合不再重复。关键词只来自当前需求版本的锚点、支持词、待试词或公司词。三轮全部服务于主池，title 范围、公司层、城市层中途保持不变。
- **hard_filters**：全部明确的硬性筛选条件，以及排除信号中简历正文能验证的项。
- **semantic_criteria**：必须满足、加分项、排除信号，照录当前需求版本。
- **requirement_version**：写入当前已确认需求版本。同一版本只允许调整查询，不得替换或删除 hard_filters、semantic_criteria。

写完运行校验：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts-local/scripts/ledger.py" check-plan --task-work-dir "/ABSOLUTE/TASK_WORK_DIR" --iteration N
```

校验失败时按错误原因原地修正同一个 iteration-N.json 再校验一次，这一轮不对用户输出任何字；仍失败则停止。

完成标准：check-plan 返回 ok，两路查询和评分项都能回溯到当前需求版本。

### 7. 派检索子 Agent

**播报**（派发前，必须预告）：本轮用哪几组词、期间不会有新消息。例："第 2 轮开始，这轮用「Agent + LangGraph」和「Agent + RAG」两组词在本地简历库里找，期间不会有新消息。"

写任务单 `briefs/iteration-N.json`（`mode=round`、`prf=true`），按「检索子 Agent」一节派发并 merge。子 Agent 一次完成：两路检索、对照台账去重、硬筛、按上限挑人（主路径 5、第二路 3）、需要时**补搜**、评分、PRF。

**补搜**由子 Agent 按 `references/retrieval.md` 自行判断和执行：主路径带了公司词、该公司不是硬条件、可评人数不足主路径上限时，去掉公司词再搜一次，补足差额。每轮最多一次，不计入轮次，也不代替扩张。回执 `refill` 非空说明补搜过，按步骤 4 把该公司标「人不够」。

完成标准：回执已打印；台账和评分表已由脚本更新。

### 8. 读回执

先看 `status` 和 `tool_events`。检索工具每个非成功状态都有 code 和 next_action，按下表处理：

| 状态 | 处理 |
| --- | --- |
| `LIBRARY_NOT_CONFIGURED` | 本机还没有可搜索的已整理简历。告诉用户：「本机还没有整理好的简历，请点左侧「整理简历」→「添加文件夹」或「添加Excel简历表」，整理完成后再来找我。」停止本 Skill，不出报告。 |
| `NO_MATCHES` | 该查询零结果，是有效结果，照常进入后续步骤；不代表用户没整理过简历。 |
| 索引中 / 来源失效 / 整理失败 | 按 message 向用户说明对应处理方式；子 Agent 已停在该处，本轮按已有结果继续。 |
| 限频 / 连接错误 | 失败，不记作零结果；本轮按已有结果继续，下一轮照常发起。 |

`coverage_warning` 非空时，本轮播报里加一句检索覆盖不完整、原因是什么。

再用回执更新决策记录：`labels` 用于尺度确认、扩张门和播报；`company_hits` 按步骤 4 并入公司池；`prf_decision` 记为本轮 PRF 判定（同一轮后一次运行的判定覆盖前一次）；`remaining` 留给步骤 10 挑人。

完成标准：每个 tool_event 都已按上表处理；公司池、PRF 判定已写入决策记录。

**播报**：用了哪些词、各找到多少人、多少人条件对得上、几位之前看过所以跳过、本轮评了几人、新增几位值得推荐、几位很匹配、名单上现在几人；补搜过就把两次的人数说在一段里；从这些人里新记下几家公司（只说数量）。第 1 轮这则播报之后进入步骤 9；第 2 轮起进入步骤 10。

### 9. 尺度确认（仅第 1 轮）

本轮回执 `labels` 非空时，先给用户看判断样例，再决定是否扩张。`labels` 为空就进入步骤 11。第 2 轮起不执行本步。

样例从本轮 `labels` 里取 2 位值得推荐的（优先很匹配）和 1 位不推荐的；某一类不足就有几位写几位。每人两行，第一行是什么样的人，第二行是这样判的理由，内容取自 `scores.json` 里该人的 `card` 和 `evidence_summary`。姓名、分数和公司全称留在记录里，公司写成行业或类型。

先把这几则样例用普通文本输出，再调用 request_user_input，step_id=calibrate，prompt 一句「这个尺度对吗？」。单选，推荐「尺度对，继续找」：

- 「[推荐] 尺度对，继续找」
- 「偏松，这样的人不该推荐」（allow_custom，填写哪一条必须满足或加分项要更严）
- 「偏严，这样的人可以推荐」（allow_custom，填写哪一条可以放宽）

选了尺度对，用本轮回执进入步骤 10。选了偏松或偏严且写明了改哪一条：只改那一条，按 `references/requirements-draft.md` 写新版本，不重新确认画像；再派一次重评（`mode=rescore`，重评全部已评的人，`prf=true`，`correction_reason` 写「尺度调整」），用重评回执的 `labels`、`expansion_gate` 进入步骤 10。没写清改哪一条时，用同一步再问一句。

完成标准：已拿到用户选择；若改了标准，新版本文件已写入，已评的人已按新版本重评，扩张门用的是重评后的回执。

**播报**：尺度照旧，或改了哪一条、已按新标准重新看过；接下来是继续从这批结果里多看几位，还是先到此为止。

### 10. 轮内扩张（可选，可重复）

回执 `expansion_gate` 为 true 时，按 `references/seen-and-expand.md` 从 `remaining` 挑人并派扩张运行；为 false 进步骤 11。

完成标准：每次扩张都有任务单、run 文件和回执；挑人依据在决策记录里。

### 11. 反思（只有建议权）

按 `references/reflect.md`，用本轮全部回执、目标公司池、当前词表和本轮 PRF 判定，把反思建议写进决策记录，交给步骤 12。

完成标准：反思建议对活跃词、下一公司各有表态。

### 12. Controller 决策

**强池** = Top 10 已满且强匹配 ≥ 5，以最新回执的 `totals.strong_pool` 为准。

**最大轮次** = min(轮次预算, 3)。**已完成轮数**是本轮在内、已经执行完步骤 6–12 的轮数；轮内扩张和补搜不改变轮数。开始第 N+1 轮的唯一条件是"已完成轮数 < 最大轮次"且下面的判定为继续：已完成 2 轮时 2 < 3，第 3 轮照常开始并完整执行。

Controller 是停止与下一轮关键词的最终决策者，按下列优先级判定：

1. 致命错误（含 `LIBRARY_NOT_CONFIGURED`），或 merge 报错两次 → 终止，不报告终态。
2. 已完成轮数 ≥ 最大轮次 → 硬停。
3. 没有任何可执行查询（活跃词、备用词、待试词、仅锚点查询都已用尽）→ 以"词族耗尽"异常终止。
4. 质量门：强匹配 ≥ 3 或已成强池 → 可停；但有新候选人的轮次不足 2 且仍有未试词族 → 继续。强匹配 < 3 时：有未试词族 → 继续；没有 → 先放宽一次（激活备用词或换相邻写法）再允许低质量停止。
5. 救援（决定继续但没有可选活跃词族时，按序执行一步）：激活备用词 → 试跑已存在的待试词 → 仅主锚点查询（最多一次）→ 以"词族耗尽"停止。

继续时：输出下一轮主路径关键词（含下一个公司词，如有），对反思建议逐条表态（接受 / 部分接受 / 拒绝），回到步骤 6。停止时：记录确定性停止原因——强匹配足够、新增候选不足、多轮无进展、达到最大轮次、词族耗尽、预算——进入步骤 13。

完成标准：决策记录里要么有确定性停止原因，要么有下一轮关键词，并且对反思建议逐条写了接受、部分接受或拒绝。

**播报**（每轮小结）：这轮各组词带来多少新人、多少是之前看过的；累计多少位值得推荐、多少位很匹配；继续就说下一轮换哪组词和原因，停止就说原因并告诉用户马上给报告。

### 13. 终态报告

运行：

```
python "/ABSOLUTE/BUILTIN_SKILLS_DIR/wts-local/scripts/ledger.py" settle --task-work-dir "/ABSOLUTE/TASK_WORK_DIR"
```

它写出 `<TASK_WORK_DIR>/wts-local/final-report-data.json`。报"还有人未重评"时先派重评再 settle。

写市场观察之前，按 `references/market-research.md` 自己做市场求证。本地库的人数和分数只用 settle 结果；公开资料用求证结论和来源。再按 `references/final-report.md` 写 report.json 并渲染用户视图，不重新检索、不重新评分。

完成标准：report.json 已写入且带 `seen_ledger_path`；用户视图里每位推荐候选人都有一行和简历文件位置。

### 14. 方向选择

终态报告输出后，调用 request_user_input，step_id=next-direction，用白话问一句"这个方向找完了，要不要换个方向继续找？"，单选，允许自定义：

- 每个备选方向一个选项，写成招聘用户听得懂的一句话（"从做过 XX 的人里继续找"）。
- 固定加一个"先到这里"选项。没有备选方向时只留这一项。
- 推荐一项并附依据：可推荐人数未达目标且有备选方向时推荐最接近主池的那个；已达目标或没有备选方向时推荐"先到这里"。

这是本 Skill 的最后一个动作。用户的选择在本 Skill 之外处理：选了某个方向，那是一次新的寻访任务，从步骤 1 重新开始，主池即该方向；选了先到这里，结束。

完成标准：request_user_input 已发出，选项是全部备选方向加上"先到这里"，其中一项标了推荐。

## 决策规则

- 主 Agent 只消费回执、`scores.json` 里的 `card` / `evidence_summary` / `short_reason` 和 settle 结果。可推荐、强匹配、Top 10、扩张门以回执为准。`search_local_resumes` 只由检索子 Agent 调用；`retrieval.md`、`scoring.md`、`prf.md` 与简历原文只给子 Agent 读。
- 性别、学校名称、民族、婚育不写入检索、硬筛、评分、排序、硬冲突判定或市场洞察。用户提出时说明不予执行，其余条件照常处理。
- 零结果（`NO_MATCHES`）是有效的查询结果，进入正常的评分、反思和 Controller 决策；工具错误、限频、连接失败是失败，不记作零结果。
- 简历正文里没有出现的经历记 unknown，不当作候选人不具备。
